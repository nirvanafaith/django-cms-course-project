# 北京交通大学课程 CMS 项目技术选型与答辩教案

> 面向对象：没有系统学过编程、需要准备课程设计答辩的同学
>
> 项目类型：Django 服务端渲染内容管理系统
>
> 阅读目标：读完后能够用自己的话说明“系统由什么组成、为什么这样选、组件之间怎样通信、一次请求怎样完成”，并能够回答老师常见的技术问题。

---

## 0. 先给出一句话介绍

本项目是一个使用 **Python 3.12 和 Django 5.2** 开发的北京交通大学风格内容管理系统。普通访问者可以浏览已发布文章、按标题、日期和栏目组合查询内容；管理员可以登录 Django Admin 管理用户、栏目和文章；系统使用 **PostgreSQL 18.6** 保存业务数据，使用 **Redis 7.4** 保存缓存和限流状态，使用 **Waitress** 提供 Web 服务，使用 **WhiteNoise** 提供静态文件，最后用 **Docker Compose** 把这些服务组织起来。

最重要的架构结论是：

```text
浏览器
  ↓ HTTP 请求
Waitress
  ↓ WSGI
Django
  ↓ 中间件
URL 路由 → View 视图 → Form 表单 / Selector 查询器
                         ↓
                   Django ORM
                    ↙      ↘
          PostgreSQL       Redis
       业务事实数据     缓存、限流状态
                         ↓
              Django Template 模板
                         ↓
                    HTTP 响应
```

这里有一个容易被问到的重点：**本项目不是 Vue/React + Spring Boot 的前后端分离项目，也没有单独的 REST API 服务。** 它是一个 Django 服务端渲染的单体应用。浏览器提交请求后，Django 在服务器上读取数据、套用 HTML 模板、生成完整网页，再把网页返回给浏览器。

## 2. 先学会看系统架构

### 2.1 什么是架构

“架构”可以先理解成一栋楼的结构图。它回答三个问题：

- 系统有哪些房间，也就是哪些组件？
- 每个房间负责什么，不负责什么？
- 房间之间通过什么通道交流？

本项目使用的是 **服务端渲染单体架构**。

#### 单体是什么意思

单体不是说代码只有一个文件，而是说主要业务功能部署在一个 Django Web 应用里。项目中没有拆成多个独立的业务微服务，公开内容、登录、后台管理、健康检查、日志查看等功能都由同一个 Django 项目提供。

单体架构的优点是：

- 项目结构直观，适合课程设计和小型系统。
- 调试简单，浏览器请求和后端代码在同一个项目内容易追踪。
- 部署成本低，只需要维护一个 Web 应用和它依赖的数据库、缓存。
- Django 的认证、Admin、ORM、模板等功能可以直接复用。

单体架构的限制是：

- 所有业务共享一个应用进程，规模变大后模块之间可能互相影响。
- 如果用户量非常大，不能只靠增加一台单体服务器解决所有问题，还要进一步做拆分、负载均衡或服务水平扩展。

对本课程项目来说，业务规模和功能边界适合单体架构，没有必要为了“看起来高级”而拆成微服务。

#### 服务端渲染是什么意思

网页有两种常见生成方式：

1. **服务端渲染**：服务器先把数据填入 HTML 模板，返回完整 HTML。
2. **客户端渲染**：服务器主要返回 JSON，浏览器中的 Vue、React 等前端框架再生成页面。

本项目采用第一种。比如访问文章详情页时，Django 读取 `Item` 文章对象，把它交给 `content/item_detail.html`，模板生成标题、栏目、正文和日期，再返回给浏览器。

### 2.2 项目的模块划分

项目根目录中的 `cms_site/` 是 Django 工程目录，里面主要分成三个 Django 应用和两类界面资源：

| 模块 | 主要职责 | 小白理解 |
| --- | --- | --- |
| `config` | 设置、总路由、WSGI 入口 | 总电闸和总地图 |
| `content` | 栏目、文章、查询表单、公开页面、文章 Admin | CMS 的业务核心 |
| `core` | 健康检查、缓存、限流、日志、后台权限、Waitress 启动命令 | 通用基础设施 |
| `config.env` / `config.backends` / `config.security` | 环境变量、数据库/缓存后端和安全配置 | 启动前的配置管家 |
| `templates` | HTML 模板 | 网页骨架和占位符 |
| `static` | CSS、JavaScript、图片 | 网页样式、交互和素材 |
| `tests` | 自动化测试 | 自动检查系统是否符合约定 |

这种拆分体现了一个重要原则：**业务代码和基础设施代码分开**。`content` 关心“文章是什么、如何查询”；`core` 关心“请求如何记录、缓存如何工作、服务是否健康”。

## 3. 前端技术选型

### 3.1 前端到底使用了什么

本项目的前端技术是：

- Django Templates：由服务器生成 HTML。
- HTML：描述页面结构和语义。
- 原生 CSS：负责颜色、排版、布局、响应式和可访问性样式。
- 原生 JavaScript：负责移动导航和首页轮播。
- 本地图片和 SVG：提供校名标识、轮播素材和网站图标。

项目**没有使用**：

- Vue、React、Angular 等前端框架。
- Bootstrap、Tailwind 等 CSS 框架。
- jQuery、Axios 等额外前端库。
- 外部图片热链接。

这不是技术不够先进，而是本项目的需求更适合“少依赖、容易解释、可控性高”的方案。

### 3.2 Django Templates 是什么

模板可以理解成“带空格的 HTML 文档”。固定的页面结构写在模板里，变化的数据使用 Django 模板变量填入。

例如，`templates/base.html` 定义了所有页面都共用的基础结构：

- HTML 文档类型和中文语言属性。
- 页面标题。
- CSS 文件引用。
- 顶部导航。
- 页面主体占位区。
- 页脚。
- `main.js` 脚本引用。

子页面通过模板继承复用这个骨架。这样做的好处是：修改导航或页脚时，不需要逐个修改所有页面。

模板里常见的三种语法是：

```django
{{ page_title }}
```

表示读取一个变量。

```django
{% if messages %}
    显示消息
{% endif %}
```

表示条件判断。

```django
{% include "partials/nav.html" %}
```

表示包含一个可复用的模板片段。

### 3.3 为什么不使用 Vue 或 React

可以从项目实际需求回答：

1. 本项目主要是内容浏览、查询、登录和后台管理，页面不需要大量实时局部刷新。
2. Django Templates 已经能直接把 ORM 数据渲染成 HTML。
3. 使用原生 CSS 和 JavaScript 可以减少 Node.js 构建链、前端依赖和打包配置。
4. 对课程答辩而言，请求从路由到模板的链路比较短，容易演示和解释。
5. Django Admin 本身就是服务端页面，使用统一的服务端渲染模式更自然。

如果将来做在线编辑器、实时聊天、复杂拖拽看板或高频局部刷新，Vue/React 可能更合适；但那属于不同的需求，不应为了使用框架而使用框架。

### 3.4 CSS 的组织方式

`static/css/` 中的 CSS 按职责分开：

| 文件 | 作用 |
| --- | --- |
| `tokens.css` | 颜色、字体、间距等设计变量 |
| `custom.css` | 通用基础样式 |
| `chrome.css` | 顶部导航、页脚等页面外壳 |
| `home.css` | 首页和轮播样式 |
| `content.css` | 文章列表、搜索、详情样式 |
| `responsive.css` | 移动端和不同屏幕宽度适配 |
| `admin.css` | 后台页面的品牌化样式 |

项目中的 `DESIGN.md` 是设计规则的说明文件，规定了颜色令牌、最大内容宽度、断点、触控目标、键盘操作和减少动态偏好等。

### 3.5 JavaScript 做了什么

`static/js/main.js` 是原生 JavaScript 文件，主要有两类行为：

#### 移动导航

- 找到导航展开按钮。
- 点击时切换菜单打开/关闭状态。
- 更新 `aria-expanded` 和 `aria-label`，让辅助技术知道菜单状态。
- 按 `Escape` 键关闭菜单。

#### 首页轮播

- 识别所有轮播图片。
- 支持上一张、下一张。
- 支持暂停和继续自动播放。
- 支持键盘左右方向键。
- 每 6 秒自动切换一次。
- 识别 `prefers-reduced-motion: reduce`，用户选择减少动态时关闭自动播放。

这个脚本不负责读取数据库，也不调用后端 API。它只操作服务器已经返回到浏览器中的 DOM。**前端交互和后端数据业务是两个层次。**

### 3.6 前端选型特点

| 特点 | 具体体现 |
| --- | --- |
| 依赖少 | 不使用前端框架和 CSS 框架 |
| 易解释 | HTML、CSS、JS 文件可以直接打开阅读 |
| 服务端统一 | 业务页面和 Django Admin 都由 Django 返回 |
| 可访问性 | skip link、可见焦点、ARIA 属性、键盘操作、44px 触控目标 |
| 响应式 | 992px 折叠导航、767px 双栏堆叠、480px 收紧间距 |
| 可维护 | 基础模板、局部模板、CSS 分文件和设计令牌 |

## 4. 后端技术选型

### 4.1 Python 3.12

Python 是本项目的主要编程语言。选择它的原因：

- 语法相对易读，适合课程项目和初学者理解。
- Django 生态成熟，包含认证、Admin、ORM、模板和测试框架。
- 适合快速开发数据库驱动的网站。
- Python 的类型标注、格式化和静态检查工具可以提升代码质量。

本项目通过 `pyproject.toml` 指定 Python 3.12，并使用 BasedPyright 进行类型检查。

### 4.2 Django 5.2

Django 是 Python Web 框架。框架可以理解成一套已经搭好的房屋结构，开发者只需要按照约定填入业务代码。

本项目使用了 Django 的这些能力：

| Django 能力 | 项目用途 |
| --- | --- |
| URL 路由 | 把 URL 分配给对应视图 |
| View 视图 | 处理 HTTP 请求并生成响应 |
| Form 表单 | 校验用户输入 |
| Model 模型 | 用 Python 类描述数据库表 |
| ORM | 用 Python 查询数据库，避免手写大部分 SQL |
| Template | 用数据生成 HTML |
| Auth | 用户、密码和登录会话 |
| Admin | 快速生成管理后台 |
| Middleware | 在请求前后统一执行公共逻辑 |
| Migration | 记录并同步数据库结构变化 |
| TestCase | 编写数据库和页面测试 |
| Staticfiles | 管理 CSS、JS、图片等静态文件 |

### 4.3 URL 路由

总路由在 `config/urls.py`。它先处理管理、登录、健康检查，再把根路径交给 `content.urls`。

例如：

```text
/search/       → content.views.search
/item/12/      → content.views.item_detail(pk=12)
/health/live/  → core.views.health_live
```

路由的职责是“找到应该处理这个请求的代码”，它不应该承担复杂的数据库查询。

### 4.4 View 视图

视图是浏览器和内部业务代码之间的适配层。`content/views.py` 中的三个主要视图职责很清楚：

- `index`：准备首页数据并渲染 `content/index.html`。
- `item_detail`：查找一篇已发布文章，找不到则返回 404。
- `search`：读取 GET 查询参数，调用 `SearchForm` 校验，再调用查询器和分页工具。

视图不直接写复杂 SQL，也不把所有逻辑堆在一个函数里。这体现了“单一职责”思想。

### 4.5 Form 表单

`SearchForm` 是搜索输入的第一道边界。它负责：

- 读取关键词 `q`。
- 去掉关键词首尾空白。
- 限制关键词最多 100 个字符。
- 按 `YYYY-MM-DD` 解析日期。
- 从数据库中的真实栏目生成栏目选择项。
- 拒绝开始日期晚于结束日期。
- 拒绝超过 366 天的查询范围。

为什么要使用 Form，而不是直接在 View 中取参数？

因为表单把“用户输入是什么”转换成“后端可以信任的 Python 值”。View 只需要处理校验后的结果，查询器也不需要关心原始字符串。

### 4.6 Selector 查询器

`content/selectors.py` 只负责只读数据库查询，不读取 `HttpRequest`，不决定 HTML，也不决定 HTTP 状态码。

它集中保存了三个重要规则：

1. 公开页面只能查 `is_published=True` 的文章。
2. 按 `-publish_time, -pk` 稳定排序。
3. 使用 `select_related` 预先读取栏目和作者，避免模板渲染时发生 N+1 查询。

把查询规则集中到 Selector 的好处是：

- 首页、搜索页、详情页可以复用同一套公开数据规则。
- 查询可以单独测试。
- View 更像“流程编排”，答辩时容易解释。
- 不会因为某个页面忘记过滤草稿而把内部内容公开出去。

### 4.7 QuerySet 惰性求值

Django ORM 的 QuerySet 默认不是调用一行就立刻访问数据库。它先构造一个“待执行的查询描述”，直到需要遍历、分页、`list()`、`exists()` 等操作时才真正执行 SQL。

例如：

```python
items = Item.objects.published()
items = items.filter(title__icontains="通知")
items = items.order_by("-publish_time")
```

上面几行可以继续链式组合条件，最后在模板遍历时才访问数据库。这样既方便组合查询，也避免提前查询无用数据。

### 4.8 为什么公开页面隐藏草稿

公开查询统一从 `is_published=True` 开始；详情页也只查询已发布文章。如果访问草稿的主键，视图把 `DoesNotExist` 转换成 404。

这样设计有两个效果：

- 用户看不到草稿正文。
- 用户也无法通过“文章编号存在”推断某篇草稿是否存在。

这是一个典型的“业务规则必须集中执行”的例子。

## 5. 数据库选型：PostgreSQL 18.6

### 5.1 PostgreSQL 是什么

PostgreSQL 是关系型数据库。关系型数据库把数据放在有结构的表中，表由行和列组成，并且可以通过主键、外键、索引和事务保证数据关系与一致性。

本项目明确规定 PostgreSQL 18.6 是唯一业务数据库。项目不是“开发环境 SQLite、生产环境 PostgreSQL”的混合方案。

### 5.2 为什么选 PostgreSQL

本项目选择 PostgreSQL 的理由：

1. **关系模型适合 CMS**：文章属于栏目，文章可以关联作者，天然适合外键关系。
2. **数据一致性强**：外键、事务和约束可以阻止非法数据。
3. **查询能力完整**：支持组合条件、排序、分页和复杂索引。
4. **搜索扩展成熟**：项目使用 `pg_trgm` 和 GIN 索引优化标题模糊搜索。
5. **部署和测试统一**：开发、测试、演示都使用 PostgreSQL，避免数据库语义不一致。
6. **Django 集成成熟**：使用 Django PostgreSQL 后端和 Psycopg 3 连接。

### 5.3 数据表设计

核心业务表有两张：

#### `content_category` 栏目表

| 字段 | 含义 |
| --- | --- |
| `id` | 主键，自动生成 |
| `name` | 栏目名称，唯一 |
| `description` | 栏目简介，可为空 |
| `created_at` | 创建时间，自动记录 |

#### `content_item` 文章表

| 字段 | 含义 |
| --- | --- |
| `id` | 主键 |
| `title` | 标题，最多 200 字符 |
| `content` | 正文 |
| `publish_time` | 发表时间 |
| `updated_at` | 最近修改时间 |
| `is_published` | 是否公开发布 |
| `category_id` | 所属栏目外键 |
| `author_id` | 作者外键，可为空 |

Django 认证还会产生 `auth_user` 等框架表，用来保存用户、权限、会话相关数据。Django Admin 的操作审计使用 `django_admin_log`。

### 5.4 外键删除策略

文章到栏目使用：

```python
on_delete=models.PROTECT
```

含义是：如果栏目下仍有文章，就不允许删除栏目。这样可以避免文章突然变成“没有栏目”的孤儿数据。

文章到作者使用：

```python
on_delete=models.SET_NULL
```

含义是：作者被删除后，文章仍然保留，只把 `author_id` 设为空。因为文章历史内容比作者账户更重要。

这两个策略体现了不同的业务优先级：

- 栏目是文章分类关系的一部分，不能破坏。
- 作者是文章的附加信息，作者消失后可以保留文章。

### 5.5 索引设计

项目为 `Item` 建立了三类索引：

| 索引 | 支撑的查询 |
| --- | --- |
| `item_pub_time_idx` | 按发布状态和发布时间查询首页、公开列表 |
| `item_cat_pub_time_idx` | 按栏目、发布状态和发布时间查询 |
| `item_title_trgm_idx` | 已发布文章的标题模糊搜索 |

索引可以理解成书的目录。没有索引时，数据库可能需要逐行查看全部文章；有合适索引时，可以更快定位符合条件的数据。但索引也会占用空间，并且新增、修改数据时需要维护，因此不能无限增加。

### 5.6 `pg_trgm` 和 GIN 索引

标题搜索使用 PostgreSQL 的 `pg_trgm` 扩展。三元组是把字符串拆成相邻的三个字符片段，用于支持包含、相似度等文本搜索。

项目迁移中启用了 `TrigramExtension`，并为 `UPPER(title)` 建立了部分 GIN 索引。部分索引只针对已发布文章，因此不会把草稿纳入公开搜索索引。

答辩时可以这样说：

> 普通 B-tree 索引适合等值和范围排序；标题包含搜索可能需要检查大量文本，所以项目使用 PostgreSQL 的 pg_trgm 扩展和 GIN 索引。索引还加了 `is_published=True` 条件，既符合业务边界，也减少无用索引项。

### 5.7 时间和时区

项目使用：

- `TIME_ZONE = "Asia/Shanghai"`
- `USE_TZ = True`

搜索的日期不是简单地把当天解释成 UTC，而是按上海自然日解释。比如用户选择结束日期 `2026-08-13`，系统实际转换成：

```text
publish_time >= 2026-08-13 00:00:00 Asia/Shanghai
publish_time <  2026-08-14 00:00:00 Asia/Shanghai
```

使用“下一天零点之前”的开区间，可以包含结束日期当天的全部时间，例如 23:59:59 的文章也不会被漏掉。

### 5.8 事务和迁移

**迁移 Migration** 是数据库结构的版本控制。模型增加字段、索引或约束后，通过迁移文件让数据库逐步更新，而不是手动修改数据库。

项目中的迁移包括：

- `0001_initial.py`：创建栏目和文章模型。
- `0002_postgresql_constraints_indexes.py`：启用 `pg_trgm`，增加索引，调整发布默认值。
- `0003_upper_title_trigram_index.py`：把标题三元组索引调整为 `UPPER(title)` 的已发布部分索引。

`seed_data` 使用 `transaction.atomic()`，用户、栏目和文章同步要么整体成功，要么整体回滚，避免只写入一半数据。

### 5.9 为什么不用 SQLite

SQLite 适合极小型本地演示，但本项目选择统一 PostgreSQL，原因是：

- SQLite 和 PostgreSQL 的字段、索引、并发和 SQL 行为并不完全相同。
- `pg_trgm` 和 GIN 索引是 PostgreSQL 能力。
- 如果开发时用 SQLite，测试通过并不代表 PostgreSQL 上的查询和迁移一定正确。
- 课程要求重点展示 PostgreSQL 技术能力，因此统一数据库更容易提供可信证据。

## 6. Redis、中间件和日志

### 6.1 Redis 是什么

Redis 是一个以内存读写为主的键值存储。它通常适合：

- 缓存页面数据。
- 保存短时间计数器。
- 保存限流状态。
- 保存可以丢失、可以重新生成的数据。

本项目的核心事实数据仍然在 PostgreSQL。Redis 只保存可重建状态，不能替代业务数据库。

### 6.2 Redis 在项目中的两个用途

#### 公开页面缓存

`core/caching.py` 为首页和文章详情生成缓存键：

```text
cms:page:v1:home
cms:page:v1:item:<文章主键>
```

首页缓存 30 秒，文章详情缓存 60 秒。读取流程是：

1. 先从 Redis 读取。
2. 命中就直接返回缓存数据。
3. 未命中就查询 PostgreSQL。
4. 把查询结果写入 Redis。
5. 返回结果。

文章发布状态改变后，Admin 使用 `transaction.on_commit()` 在数据库事务真正提交后失效缓存。这样不会因为事务后来回滚，导致缓存被提前删除或出现错误状态。

#### 访问和登录限流

公开 GET 请求按“客户端地址 + 页面路径”计数。后台登录失败则按用户名摘要和客户端 IP 组合计数。

项目使用固定窗口计数：

- 公开访问：默认 60 秒窗口内最多 6000 次。
- 管理员登录失败：默认 300 秒内失败 5 次后封禁 900 秒。

实际参数以 `settings.py` 和环境变量为准。

### 6.3 Redis 不可用时怎么办

项目根据场景采用不同策略：

- 本地公开页面：Redis 故障时可以跳过缓存，直接读取 PostgreSQL，保证浏览继续工作。
- 公网登录保护：Redis 故障时不能假装限流仍然有效，否则可能绕过登录保护；公网模式会失败关闭或返回不可用。
- 就绪检查：Redis 不能写入并读回健康键时，`/health/ready/` 返回 503。

这说明“降级策略”不能一刀切。缓存故障可以接受性能下降，安全控制故障可能必须停止服务。

### 6.4 Django Middleware 是什么

Middleware 可以理解为包在每个请求外面的公共处理层。它们按顺序执行，可以在进入视图前检查请求，也可以在视图返回后修改响应。

项目中重要的中间件包括：

| 中间件 | 作用 |
| --- | --- |
| `SecurityMiddleware` | Django 通用安全处理 |
| `WhiteNoiseMiddleware` | 直接提供静态文件 |
| `RequestContextMiddleware` | 生成请求 ID、记录耗时、写响应头 |
| `PublicRateLimitMiddleware` | 限制公开 GET 请求 |
| `SessionMiddleware` | 读取和保存登录会话 |
| `CsrfViewMiddleware` | 保护 POST 表单免受 CSRF 攻击 |
| `AuthenticationMiddleware` | 将用户身份放入请求 |
| `AdminLoginThrottleMiddleware` | 保护登录失败次数 |
| `MessageMiddleware` | 页面消息提示 |
| `XFrameOptionsMiddleware` | 防止页面被恶意嵌入 |

### 6.5 请求 ID 和结构化日志

`RequestContextMiddleware` 每次请求生成 UUID：

```text
X-Request-ID: 3a3f...
```

同时记录：

- 请求方法。
- 请求路径。
- HTTP 状态码。
- 耗时。
- 用户 ID（满足条件时）。
- 脱敏后的 IP。

日志采用 JSONL 格式，即“一行一个 JSON 对象”，适合机器检索和日志平台收集。日志按天轮转，保留 14 天。

项目有两个重要日志类别：

- `cms.request`：请求完成日志。
- `cms.security`：限流、登录失败等安全事件。

日志不记录查询字符串、Cookie、密码、正文和授权头，减少敏感信息泄露风险。

### 6.6 Admin 审计日志和系统日志的区别

| 日志 | 来源 | 记录内容 |
| --- | --- | --- |
| Django `LogEntry` | Django Admin | 管理员对对象的新增、修改、删除操作 |
| `cms.jsonl` | 自定义日志配置 | 请求、限流、登录失败等系统运行事件 |

Admin 中的 `LogEntry` 被配置成只读，不能通过后台修改或删除审计记录。自定义日志页面支持日期、级别、事件、状态和请求 ID 过滤，并限制读取数量和分页。

## 7. Web 服务、WSGI 和静态文件

### 7.1 WSGI 是什么

WSGI 是 Python Web 服务器和 Web 应用之间的接口标准。可以把它理解为“统一插座”：

- Waitress 是服务器插头。
- Django 是应用本体。
- `config/wsgi.py` 提供两者都认识的 `application` 对象。

`config/wsgi.py` 的核心代码是：

```python
application = get_wsgi_application()
```

Waitress 导入这个 `application` 后，就可以把 HTTP 请求交给 Django。

### 7.2 为什么选 Waitress

Waitress 是纯 Python 的生产级 WSGI 服务器，适合本项目：

- Windows 和 Linux 都容易运行。
- 不需要额外的 C 编译依赖。
- 配置线程数、连接数、请求大小比较直接。
- 比 Django 自带开发服务器更适合正式演示和部署。

Django 自带的 `runserver` 主要用于开发调试，不建议作为公网生产服务器。

项目中的 `serve_waitress` 命令设置了：

- 默认 8 个线程。
- 连接上限 100。
- 请求队列长度 128。
- 请求头最大 16 KB。
- 请求体最大 10 MB。
- 不向用户暴露 traceback。
- 信任代理头前先根据配置验证代理。

### 7.3 WhiteNoise 是什么

CSS、JavaScript、图片这类文件叫静态文件。WhiteNoise 允许 Django 应用直接提供这些文件，不必额外部署 Nginx 才能完成课程项目的静态资源服务。

公网模式使用压缩和带 manifest 的静态文件存储：

```text
whitenoise.storage.CompressedManifestStaticFilesStorage
```

部署时先运行：

```text
python manage.py collectstatic --noinput
```

它会把各处静态资源收集到 `staticfiles/`，供 Web 服务使用。

### 7.4 前端资源是怎样返回的

以 CSS 为例：

1. `base.html` 使用 `{% load static %}` 和 `{% static 'css/tokens.css' %}` 生成资源 URL。
2. 浏览器收到 HTML 后，再请求 `/static/css/tokens.css`。
3. WhiteNoise 找到收集后的文件并返回 CSS。
4. 浏览器应用 CSS，完成页面样式。

业务文章走 PostgreSQL，CSS 和图片走静态文件系统，两者职责不同。

## 8. Docker Compose 部署与组件通信

### 8.1 Docker 是什么

Docker 把应用和运行依赖打包进容器。容器可以理解成一个隔离的运行环境：代码、Python、第三方包和启动命令被放在一起。

项目 `cms_site/Dockerfile` 使用多阶段构建：

1. `builder` 阶段安装 Python 依赖。
2. `runtime` 阶段只复制虚拟环境和项目代码。
3. 运行用户不是 root，而是普通用户 `cms`。
4. 构建阶段预先执行 `collectstatic`。
5. 容器通过健康检查确认服务可响应。

多阶段构建的目标是减少运行镜像中不必要的构建工具，并降低权限。

### 8.2 Docker Compose 中有哪些服务

`compose.yaml` 定义了五个服务：

| 服务 | 作用 | 是否长期运行 |
| --- | --- | --- |
| `db` | PostgreSQL 18.6 | 是 |
| `redis` | Redis 7.4 | 是 |
| `migrate` | 迁移、数据库检查、种子数据、静态收集 | 否，一次性 |
| `test` | 执行测试和覆盖率门禁 | 否，一次性 |
| `web` | Waitress + Django 应用 | 是 |

### 8.3 容器之间怎样通信

Compose 会为服务创建内部网络。容器之间通过服务名通信，而不是使用宿主机 `127.0.0.1`：

```text
Web → db:5432
Web → redis:6379
```

在 Compose 网络中，`db` 和 `redis` 是 DNS 服务名。应用环境变量中的：

```text
POSTGRES_HOST=db
REDIS_URL=redis://redis:6379/0
```

就是把数据库和缓存的服务名注入给 Django。

宿主机只映射 Web 端口：

```text
127.0.0.1:8000 → web:8000
```

数据库和 Redis 没有直接暴露到宿主机，降低了不必要的外部访问面。

### 8.4 启动顺序

Compose 的关键启动顺序是：

```text
db 健康
redis 健康
       ↓
migrate 完成迁移、验证数据库、初始化数据、收集静态文件
       ↓
web 启动
```

`web` 依赖 `migrate` 成功完成。如果迁移或初始化失败，Web 不会假装正常启动。

### 8.5 为什么需要健康检查

“容器进程存在”不代表“服务已经可以使用”。例如 PostgreSQL 容器已经启动，但数据库可能还没有完成初始化。

因此项目使用两类检查：

- `health/live/`：只回答“Web 进程能不能响应”。
- `health/ready/`：检查 PostgreSQL 执行 `SELECT 1`，再检查 Redis 能否写入和读回健康键。

如果数据库或 Redis 不可用，ready 返回 HTTP 503。负载均衡器或 Compose 可以据此判断暂时不要把流量发给它。

### 8.6 `migrate` 一次性服务做什么

Compose 中的命令按顺序执行：

```text
python manage.py migrate --noinput
python manage.py verify_postgres
python manage.py seed_data
python manage.py collectstatic --noinput
```

- `migrate`：同步表结构。
- `verify_postgres`：确认数据库是符合要求的 PostgreSQL 版本。
- `seed_data`：幂等生成演示用户、栏目和文章。
- `collectstatic`：收集 CSS、JavaScript 和图片。

### 8.7 `seed_data` 为什么叫幂等

幂等的意思是：命令执行一次和重复执行多次，最终结果一致，不会无限复制相同数据。

项目使用用户名、栏目名、标题加栏目组合等自然键查找已有数据，使用 `update_or_create` 更新或创建。这样可以反复初始化演示环境，而不会得到重复的 8 个栏目和 36 篇文章。

### 8.8 为什么使用环境变量

数据库密码、Django 密钥和普通演示用户密码不应该写死在代码仓库里。Compose 从环境变量读取：

- `DJANGO_SECRET_KEY`
- `POSTGRES_DB`
- `POSTGRES_USER`
- `POSTGRES_PASSWORD`
- `DEMO_USER_PASSWORD`
- `REDIS_URL`

环境变量让同一套代码可以在开发、测试和部署环境使用不同配置，也避免把真正的密钥提交到 Git。

注意：仓库 README 中用于课程演示的管理员固定账号是 `CTX`，密码是 `1234`。这类固定演示密码不能用于真正生产系统，答辩时应主动说明它只用于演示。

### 8.9 配置模块为什么单独拆出来

项目没有把所有环境变量解析逻辑直接堆在 `settings.py` 中，而是拆成三个配置模块：

| 模块 | 作用 |
| --- | --- |
| `config/env.py` | 读取运行模式、布尔值、整数和逗号分隔列表，并检查必填变量 |
| `config/backends.py` | 构建 PostgreSQL 数据库连接和 Redis/本地缓存后端 |
| `config/security.py` | 根据 `local` 或 `public` 模式构建 Host、CSRF、HTTPS 和 Cookie 安全设置 |

这样拆分可以让配置逻辑更容易测试，也能明确区分“代码逻辑”和“运行环境”。例如：

- 本地模式可以在 Redis 不可用时使用 Django 的 `LocMemCache` 降级缓存。
- 公网模式必须提供 `REDIS_URL`，不能因为缓存故障而绕过登录限流。
- 公网模式要求明确的 `ALLOWED_HOSTS` 和 `CSRF_TRUSTED_ORIGINS`，不允许使用 `ALLOWED_HOSTS="*"`。
- 公网模式关闭 DEBUG，启用安全 Cookie、HTTPS 重定向和 HSTS 等安全设置。

### 8.10 cpolar 在项目中的位置

项目还提供了一个可选的 Windows 公网启动链路：`启动公网系统.bat` 会调用 Django 的 `serve_public` 命令，`core/public_runner.py` 再启动 cpolar HTTPS 隧道和 Waitress。

它们之间的关系是：

```text
浏览器
  ↓ HTTPS
cpolar 公网隧道
  ↓ 本地 8000 端口
Waitress
  ↓ WSGI
Django
```

cpolar 不是业务数据库，也不是 Django 内部组件；它是把本机服务临时映射到公网的外部隧道工具。项目会从 cpolar 输出中提取唯一、合法的 HTTPS 地址，再把这个随机域名注入 `DJANGO_ALLOWED_HOSTS` 和 `CSRF_TRUSTED_ORIGINS`，避免公网请求因为 Host 或 CSRF 校验失败。

公网启动器还会先执行：

```text
manage.py check --deploy
manage.py migrate --noinput
manage.py seed_data
manage.py collectstatic --noinput
manage.py preflight --mode public
```

只有数据库、Redis 和 Django 公网安全检查通过后，才启动 Waitress。`PublicRunner` 只保存并终止自己创建的 cpolar 和 Web 子进程，避免误杀其他进程。

答辩时可以明确区分：

- Docker Compose 是标准的本地/容器部署编排方式。
- cpolar 是 Windows 公网演示的可选网络隧道，不是项目业务层必须依赖的通信协议。
- 真实生产环境通常会使用正式域名、反向代理、TLS 证书和更完整的运维体系。

## 9. 一次首页请求的完整通信过程

下面以用户在浏览器打开 `/` 为例。

### 第 1 步：浏览器发出 HTTP 请求

浏览器发送：

```http
GET / HTTP/1.1
Host: 127.0.0.1:8000
```

### 第 2 步：Waitress 接收请求

Waitress 监听 8000 端口，把 HTTP 请求转换成 WSGI 环境，再调用 `config.wsgi.application`。

### 第 3 步：Django 执行中间件

请求先经过安全中间件、自定义请求上下文中间件、公开访问限流中间件、会话和认证中间件等。

`RequestContextMiddleware` 会：

1. 生成 request ID。
2. 记录开始时间。
3. 继续调用下一个处理环节。
4. 得到响应后加上 `X-Request-ID`。
5. 记录状态码、耗时和脱敏 IP。
6. 清理当前请求上下文。

### 第 4 步：URL 路由匹配

`config/urls.py` 发现根路径匹配 `path("", include("content.urls"))`，然后 `content/urls.py` 把它交给 `content.views.index`。

### 第 5 步：View 读取缓存

`index` 判断公开页缓存是否启用。如果启用，使用：

```text
cms:page:v1:home
```

访问 Redis。

### 第 6 步：缓存命中或查询 PostgreSQL

- 如果 Redis 命中，直接得到首页数据。
- 如果 Redis 未命中，执行 `homepage_items()`。

查询器从 `content_item` 中筛选已发布文章，关联读取栏目和作者，按发布时间和主键倒序，并限制最多 24 条。

Django ORM 将 Python 查询转换成 PostgreSQL SQL，并通过 Psycopg 3 建立数据库通信。

### 第 7 步：Python 组织页面数据

View 将文章按栏目名称分组，准备 `latest_items`、`headline_items`、`teaching_items` 等模板上下文。

### 第 8 步：Django Template 生成 HTML

Django 把上下文交给 `content/index.html`。模板继承 `base.html`，插入导航、轮播、文章列表和页脚。

### 第 9 步：Waitress 返回响应

Django 返回 HTML 响应，中间件补上 request ID 并完成日志记录，Waitress 再把响应写回浏览器。

### 第 10 步：浏览器请求静态资源

浏览器解析 HTML 后，继续请求 CSS、JavaScript、图片。WhiteNoise 从静态文件目录返回这些资源，浏览器最终完成页面显示。

可以把全过程浓缩成：

```text
浏览器
  → HTTP
Waitress
  → WSGI
Django Middleware
  → URL Resolver
View
  → Cache
Redis 命中？────是────→ 组装上下文
  ↓ 否
Selector
  → Django ORM
Psycopg 3
  → PostgreSQL
  ← 文章数据
Template
  → HTML
浏览器
  → WhiteNoise 提供 CSS/JS/图片
```

## 10. 一次搜索请求如何保证正确

以访问 `/search/?q=通知&start=2026-08-13&end=2026-08-13` 为例。

### 10.1 路由和视图

路由把请求交给 `content.views.search`。视图先构造：

```python
form = SearchForm(request.GET)
```

这里使用 GET 是合理的，因为搜索是读取操作，不会修改数据库；用户也可以复制和分享查询 URL。

### 10.2 表单校验

`SearchForm` 把字符串转换成：

- 关键词：`"通知"`
- 开始日期：Python `date(2026, 8, 13)`
- 结束日期：Python `date(2026, 8, 13)`
- 栏目：一个真实的 `Category` 对象或空值

如果日期格式错误、日期顺序错误、范围过大或栏目不存在，表单无效，View 返回带错误信息的页面，并使用 `Item.objects.none()`，不会执行公开文章查询。

### 10.3 Selector 组合条件

合法输入进入 `search_published_items`：

```text
is_published = true
AND title contains "通知"
AND publish_time >= 上海时区的开始日期零点
AND publish_time < 上海时区的结束日期下一天零点
AND category = 选择的栏目（如果有）
ORDER BY publish_time DESC, id DESC
```

条件是 AND 关系，意味着输入的每个条件都必须满足。查询通过 Django ORM 参数化生成，避免把用户字符串直接拼接进 SQL。

### 10.4 分页

查询结果交给 `pagination.py`。分页不是一次把所有文章都传给浏览器，而是只取当前页需要的记录，并保留其他搜索参数，使用户翻页时查询条件不丢失。

### 10.5 为什么要使用稳定排序

如果两篇文章的 `publish_time` 完全相同，只按时间排序可能导致数据库在不同查询中返回不同顺序，进而造成分页重复或漏项。

项目使用：

```text
-publish_time, -pk
```

主键作为第二排序条件，保证顺序稳定。

## 11. 认证、权限与安全设计

### 11.1 两种用户角色

项目把用户分为：

- 普通用户：可以登录，但不是 staff，也不是 superuser。
- 管理员：同时是 staff 和 superuser。

自定义后台站点进一步要求用户处于活跃状态并且 `is_superuser=True`。只设置 `is_staff=True` 的不完整账户不能进入后台。

### 11.2 密码和会话

Django 不直接保存明文密码，而是保存密码哈希。登录成功后使用会话机制维持用户身份。

项目设置了：

- `SESSION_COOKIE_HTTPONLY = True`：JavaScript 默认不能读取会话 Cookie。
- `SESSION_COOKIE_SAMESITE = "Lax"`：降低跨站请求携带 Cookie 的风险。
- `CSRF_COOKIE_HTTPONLY = True`：加强 CSRF Cookie 保护。
- Django 密码验证器：检查相似信息、最小长度、常见密码和纯数字密码。

### 11.3 CSRF 是什么

CSRF 是跨站请求伪造。攻击者可能诱导已经登录的用户访问恶意页面，由浏览器自动带上登录 Cookie，向目标系统发送修改请求。

Django 的 CSRF 中间件要求 POST 表单带合法 CSRF token。退出操作也使用 POST，避免仅打开一个链接就改变登录状态。

### 11.4 ORM 和 SQL 注入

SQL 注入是把恶意字符串拼进 SQL 语句，改变原本查询含义。本项目使用 Django ORM 的 `filter`、`icontains`、`gte`、`lt` 等接口传递用户条件，ORM 会负责参数化，不直接把原始查询字符串拼接到 SQL 中。

模板默认会对输出进行 HTML 转义，降低文章内容产生 XSS 的风险。安全边界仍然需要在输入、模板和后台权限处分别维护。

### 11.5 限流为什么必要

公开页面限流可以降低异常爬取和突发请求压力。登录失败限流可以增加暴力猜密码的成本。

项目没有只在页面上隐藏登录入口，而是同时在服务端做权限检查。**前端隐藏按钮不等于安全，真正的权限必须在后端验证。**

## 13. 测试和质量保证

### 13.1 测试分层

项目测试覆盖了多个层次：

- 模型和数据库约束测试。
- 搜索表单输入校验测试。
- 公开页面草稿隐藏和组合查询测试。
- 查询数量和 N+1 查询测试。
- 用户登录和后台权限测试。
- Admin 批量发布、撤回和审计测试。
- Redis 缓存、限流和故障降级测试。
- JSONL 日志和日志查看测试。
- 模板、静态素材和文档合同测试。

### 13.2 为什么要测试“草稿不可见”

这是业务安全边界，不只是界面样式。测试会访问首页、搜索页和草稿详情，确认：

- 首页不出现草稿标题。
- 搜索结果不出现草稿。
- 直接访问草稿主键返回 404。

### 13.3 为什么要测试查询数量

如果模板循环中每次访问 `item.category` 都重新查询数据库，就会出现 N+1 查询：1 次查询文章，N 次查询每篇文章的栏目。

项目使用 `select_related("category", "author")`，并用 `assertNumQueries` 锁定首页和搜索页的查询预算。这样不仅测试功能正确，还测试性能底线。

### 13.4 质量检查命令

README 中给出了基本检查命令：

```powershell
.\.venv\Scripts\ruff.exe check .
.\.venv\Scripts\ruff.exe format --check .
.\.venv\Scripts\python.exe manage.py check
.\.venv\Scripts\python.exe manage.py makemigrations --check
```

Compose 测试服务执行：

```text
coverage run manage.py test --exclude-tag=postgres_performance
coverage report --fail-under=80
```

覆盖率 80% 是质量门禁，不代表“覆盖率高就一定没有 bug”，还需要结合边界测试、人工验收和安全检查。

### 13.5 性能测试为什么不能只看 36 条数据

演示数据很少时，即使没有索引，查询也可能很快。这个速度不能证明真实数据量下的性能。

项目的 PostgreSQL 性能测试会在扩展数据后执行 `ANALYZE` 和 `EXPLAIN`，观察数据库是否选择了合适的索引。答辩时可以强调：性能结论来自执行计划和扩展数据，而不是来自几十条演示记录的主观感受。

## 15. 答辩高频问题与参考回答

下面的回答不是要求逐字背诵。答辩时应先说结论，再说原因，最后结合项目文件或现象举例。

### Q1：请介绍一下你的项目架构。

**参考回答：**

本项目采用 Django 服务端渲染单体架构。浏览器请求首先进入 Waitress 和 Django 中间件，然后由 URL 路由分发到 View。View 调用 Form 校验输入，调用 Selector 通过 Django ORM 访问 PostgreSQL；Redis 用于页面缓存和限流状态；查询结果交给 Django Template 生成 HTML 返回浏览器，CSS、JavaScript 和图片由 WhiteNoise 提供。

### Q2：为什么不采用前后端分离？

**参考回答：**

本项目主要是文章浏览、组合查询、登录和管理后台，交互复杂度不高，服务端模板已经能满足需求。服务端渲染可以减少前端框架、API、打包工具和跨域配置，调用链更短，也更适合课程项目和答辩解释。如果未来需要复杂实时交互，再考虑 Vue 或 React。

### Q3：你的前端用了什么框架？

**参考回答：**

没有使用 Vue、React 等前端框架。前端使用 Django Templates、HTML、自定义 CSS 和原生 JavaScript。模板负责生成页面，CSS 负责样式和响应式，JavaScript 只负责移动导航和轮播等浏览器端交互。

### Q4：Django 的 Model、View、Template 分别是什么？

**参考回答：**

Model 描述数据结构并通过 ORM 访问数据库；View 处理请求、组织业务流程并选择要返回的响应；Template 负责把上下文数据渲染成 HTML。在本项目中，`content/models.py` 定义栏目和文章，`content/views.py` 处理首页、搜索和详情，`templates/` 负责页面展示。

### Q5：为什么选择 PostgreSQL，而不是 SQLite？

**参考回答：**

因为本项目需要统一的 PostgreSQL 数据语义、事务、外键、索引和 `pg_trgm` 标题模糊搜索。开发、测试和部署都使用 PostgreSQL，可以避免 SQLite 测试通过但 PostgreSQL 上行为不同的问题。

### Q6：PostgreSQL 在项目中保存什么？

**参考回答：**

它保存业务事实数据，包括栏目、文章、用户、Django 会话和 Admin 审计记录等。文章和栏目是核心业务表，文章通过外键关联栏目和作者。

### Q7：Redis 和 PostgreSQL 的区别是什么？

**参考回答：**

PostgreSQL 是唯一业务事实来源，负责长期保存和一致性；Redis 保存短期、可重建的缓存和限流计数。Redis 丢失后可以重新从 PostgreSQL 加载页面数据，但不能用 Redis 代替文章数据库。

### Q8：Redis 挂了系统会怎样？

**参考回答：**

公开页面缓存失败时可以降级为直接查 PostgreSQL，主要影响性能；但登录限流是安全控制，公网模式不能在 Redis 不可用时无条件放行。就绪检查会检查 Redis 的读写能力，不满足时返回 503。

### Q9：什么是 ORM？项目为什么使用 ORM？

**参考回答：**

ORM 是对象关系映射，把 Python 模型对象和数据库表对应起来。项目可以使用 `Item.objects.filter(is_published=True)` 表达查询，Django ORM 再生成参数化 SQL。这样减少重复 SQL，统一数据访问规则，也降低 SQL 注入风险。

### Q10：如果用户输入恶意 SQL，会不会注入？

**参考回答：**

公开搜索使用 Django ORM 的参数化查询，没有把用户输入直接拼接进 SQL，因此可以防止这类典型 SQL 注入。模板默认转义，POST 表单使用 CSRF 保护，后台还使用服务端权限检查。安全不能只依靠前端隐藏按钮。

### Q11：为什么要把查询写在 selectors.py，而不是全部写在 views.py？

**参考回答：**

View 负责 HTTP 流程，Selector 负责只读数据查询。这样可以集中维护“已发布过滤、稳定排序、select_related、日期范围”等规则，多个页面可以复用，查询也可以脱离请求独立测试，代码边界更清楚。

### Q12：什么是 N+1 查询？项目怎样避免？

**参考回答：**

先查出 N 篇文章，再在模板中逐篇访问栏目，可能变成 1 次文章查询加 N 次栏目查询，这就是 N+1。项目查询文章时使用 `select_related("category", "author")` 预加载外键，并用 `assertNumQueries` 测试查询预算。

### Q13：为什么查询结束日期要加一天？

**参考回答：**

因为用户选择的是一个自然日，应该包含当天从 00:00 到 23:59:59 的所有文章。项目把结束条件写成“小于下一天零点”，即 `publish_time < end + 1 day at 00:00`，这样不会漏掉结束日期当天晚些时候发布的文章。

### Q14：为什么排序要加主键？只按发布时间不可以吗？

**参考回答：**

多篇文章可能有相同发布时间。如果只按时间排序，分页时顺序可能不稳定，造成重复或漏项。增加 `-pk` 作为第二排序条件后，相同时间的文章也有稳定顺序。

### Q15：项目为什么要建立三类索引？

**参考回答：**

不同查询条件需要不同索引：发布状态加时间支撑首页和公开列表；栏目加发布状态加时间支撑栏目筛选；标题包含搜索使用 `pg_trgm` 和 GIN 索引。索引是根据实际查询路径设计的，不是越多越好。

### Q16：外键的 `PROTECT` 和 `SET_NULL` 有什么区别？

**参考回答：**

栏目使用 `PROTECT`，有文章引用时禁止删除，避免文章失去栏目。作者使用 `SET_NULL`，作者账户删除后文章保留，只把作者设为空，因为历史文章仍然有价值。

### Q17：Django Migration 是什么？

**参考回答：**

Migration 是数据库结构的版本控制。模型发生变化时，Django 生成迁移文件，部署时执行 `migrate`，让数据库按版本逐步变更。这样结构变化可审查、可重复执行，而不是依赖手动改数据库。

### Q18：Waitress 和 Django 有什么关系？

**参考回答：**

Django 是 Web 应用框架，Waitress 是 WSGI Web 服务器。Waitress 通过 `config.wsgi.application` 调用 Django，负责监听端口、接收 HTTP 请求和管理线程。两者通过 WSGI 标准连接起来。

### Q19：为什么不用 Django 自带的 runserver？

**参考回答：**

`runserver` 面向开发调试，不是正式部署服务器。项目使用 Waitress 提供有界线程池、连接数、请求大小和 traceback 隐藏等配置，更适合课程演示和部署环境。

### Q20：WhiteNoise 解决什么问题？

**参考回答：**

WhiteNoise 让 Django 应用可以直接提供 CSS、JavaScript、图片等静态文件，课程项目不需要额外部署 Nginx。部署时执行 `collectstatic`，公网模式使用压缩和 manifest 静态存储。

### Q21：Docker Compose 的作用是什么？

**参考回答：**

Docker 把运行环境隔离和打包，Docker Compose 负责定义多个容器及其网络、环境变量、健康检查和启动依赖。本项目用它统一启动 PostgreSQL、Redis、一次性迁移服务、测试服务和 Waitress Web，保证不同环境的组件版本和启动顺序一致。

### Q22：容器之间怎么找到彼此？

**参考回答：**

Compose 网络会为服务名提供内部 DNS。Web 容器通过 `db:5432` 连接 PostgreSQL，通过 `redis:6379` 连接 Redis，而不是使用容器自己的 `127.0.0.1`。宿主机只映射 Web 的 8000 端口。

### Q23：为什么要把迁移和 Web 启动分开？

**参考回答：**

迁移、PostgreSQL 版本检查、种子数据和静态收集是部署准备步骤。把它们放在一次性 `migrate` 服务中，并要求 Web 依赖它成功完成，可以避免 Web 启动后才发现表不存在、数据库版本错误或演示数据未初始化。

### Q24：`live` 和 `ready` 健康检查的区别是什么？

**参考回答：**

`live` 只确认 Web 进程能够响应；`ready` 进一步执行 PostgreSQL `SELECT 1`，并检查 Redis 能否写入和读回健康键。进程活着不代表依赖服务正常，因此部署系统应使用 ready 判断是否可以接流量。

### Q25：日志为什么使用 JSONL？

**参考回答：**

JSONL 每行是一个独立 JSON 对象，既方便人查看，也方便日志平台按字段检索。项目记录 request ID、状态码、耗时和事件类型，并按天轮转；同时不记录密码、Cookie、正文、查询串和授权头，降低敏感信息泄露风险。

### Q26：request ID 有什么用？

**参考回答：**

一次请求生成一个 request ID，并放进响应头和日志。用户报告问题时可以提供这个 ID，开发者就能在日志中定位对应请求，串起状态码、耗时和安全事件，便于排查问题。

### Q27：为什么管理员需要同时是 staff 和 superuser？

**参考回答：**

项目只定义普通用户和管理员两级角色。管理员同时设置 `is_staff=True` 和 `is_superuser=True`，并且后台自定义 `has_permission` 还会检查活跃状态和 superuser 标记。这样可以拒绝只设置一半权限的不完整账户。

### Q28：项目有什么已知风险或取舍？

**参考回答：**

题目限定了两角色模型，因此管理员之间可以互相管理，这是明确记录的取舍，生产操作需要二次确认。公开本地模式允许 Redis 缓存故障降级，但公网登录限流不能无条件降级。Django Admin 宽表格在手机上允许表格内部横向滚动，以保留管理筛选、批量操作和删除确认能力。

### Q29：如果让你继续改进，你会做什么？

**参考回答：**

我会根据实际规模再决定是否增加 CDN、反向代理、对象存储、全文搜索服务、异步任务或更细的角色权限，而不是提前引入。当前优先级可能是替换演示管理员固定密码、完善管理员分级权限、增加数据库备份自动化和补充真实负载测试。

### Q30：项目中最能体现你技术思考的地方是什么？

**参考回答：**

我认为有三个地方：第一，统一使用 PostgreSQL，避免开发和部署数据库语义不一致；第二，把查询规则集中在 Selector，并用稳定排序、索引和 `select_related` 保证正确性与性能；第三，对 Redis 故障区分缓存降级和安全控制降级，说明系统不是只考虑“正常情况”，也考虑了依赖故障时的行为。

## 17. 答辩现场演示路线

建议按“用户功能 → 管理功能 → 工程质量”演示，不要一开始就打开一堆代码。

1. 打开 `/health/live/`，说明 Web 存活检查。

### 17.4 现场表达模板

每讲一个技术点，都可以使用：

```text
这个组件是什么 → 它在本项目中负责什么 → 为什么选择它
→ 它和哪个组件通信 → 如果它故障或规模变大，会有什么影响
```

例如讲 Redis：

> Redis 是内存键值存储。在本项目中，它不保存文章事实，而是保存首页和详情缓存，以及访问限流计数。Django 通过缓存接口和 Redis 通信。缓存不可用时本地公开页可以回源 PostgreSQL，但公网登录限流不能无条件放行，所以 ready 检查会把 Redis 故障报告为 503。

## 18. 最后背熟这段两分钟总结

> 我的项目是一个基于 Python 3.12 和 Django 5.2 的内容管理系统，采用服务端渲染单体架构。前端使用 Django Templates、原生 CSS 和 JavaScript，后端按照 config、content、core 分模块组织。浏览器请求经过 Waitress、Django 中间件和 URL 路由后进入 View，View 使用 Form 校验输入，再调用 Selector，通过 Django ORM 和 Psycopg 3 访问 PostgreSQL 18.6。PostgreSQL 是唯一业务事实数据库，保存栏目、文章、用户和审计数据；Redis 7.4 只保存可重建的页面缓存和限流状态。系统使用索引、事务、外键删除策略、稳定排序和 `select_related` 保证数据正确和查询性能。Waitress 通过 WSGI 调用 Django，WhiteNoise 提供 CSS、JavaScript 和图片，Docker Compose 负责 PostgreSQL、Redis、迁移服务、测试服务和 Web 服务的网络与启动顺序。项目还实现了请求 ID、JSONL 结构化日志、健康检查、登录保护和自动化测试。整体选型遵循的原则是：在满足功能、安全、性能和可维护性的前提下，优先选择成熟、简单、容易验证和适合当前规模的技术。
