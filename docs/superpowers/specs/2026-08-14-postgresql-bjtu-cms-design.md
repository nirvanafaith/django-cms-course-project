# PostgreSQL 18 与北交大风格 CMS 完整改造设计

## 1. 目标

将现有 Django CMS 从 MySQL/SQLite 双后端彻底迁移到 PostgreSQL 18，补齐用户角色、前台登录、后台管理、操作审计、请求与安全日志、北交大主站风格前台、原创演示数据、测试和课程交付文档。

系统必须满足课程作业的核心要求：管理用户可以管理栏目和文章，普通用户可以浏览已发布内容，前台支持按文章题目、发表时间和栏目查询，并且项目能够在干净环境中复现、测试、解释和继续维护。

## 2. 已确认决策

1. “三张表”指三张核心数据表：栏目、文章和用户。Django 权限、会话、内容类型、迁移记录和管理日志等框架支撑表保留。
2. 不迁移现有 MySQL 或 SQLite 数据。PostgreSQL 18 使用全新数据库和全新演示数据。
3. 后台强化现有 Django Admin，不重复实现另一套 CRUD 后台。
4. 后台同时提供 Django 管理操作审计和近期请求/安全日志。
5. 匿名访问开放；普通用户可以登录，但不开放自助注册；账号由管理员创建。
6. 只有普通用户和管理员两种可见角色。所有管理员均为 Django 超级用户，不设置受保护的第三种系统所有者角色。
7. 前台完整复刻 `https://www.bjtu.edu.cn/` 当前主站视觉；后台只做克制的北交大品牌化。
8. 用户已确认拥有北交大官网素材的抓取和使用许可。素材下载到项目本地，并记录来源。
9. 所有运行和测试环境统一使用 PostgreSQL 18，不保留 MySQL、PyMySQL 或 SQLite 分支。
10. 初始化数据使用原创北交大风格内容，不抓取官网文章正文。
11. 请求与安全日志按天轮转并保留 14 天，管理操作审计长期保留。
12. Docker Compose 是标准部署入口，Windows BAT 是调用 Compose 的便捷入口。
13. 用户模型沿用 Django 内置 `auth.User`。

## 3. 非目标

- 不导入旧 MySQL、SQLite 数据或旧数据库卷。
- 不提供前台用户注册、找回密码、评论、投稿、富文本编辑器或附件上传。
- 不建立编辑员、审计员等第三种角色。
- 不在 PostgreSQL 中持久化每次公开访问。
- 不热链接北交大官网素材，不抓取官网文章正文。
- 不将 Django Admin 重做成门户式前台页面。

## 4. 总体架构

系统保持 Django 服务端渲染单体架构：

- `content`：栏目、文章、公开列表、详情、搜索和只读查询器。
- Django `auth`：用户、密码哈希、登录会话和超级用户权限。
- Django Admin：用户、栏目、文章 CRUD 与管理操作审计。
- `core`：请求 ID、健康检查、缓存、限流、请求与安全日志。
- PostgreSQL 18：唯一关系数据库和业务事实来源。
- Redis：公开页面缓存和限流状态，不保存业务事实。
- Waitress：WSGI 服务。
- Docker Compose：编排 PostgreSQL、Redis、迁移初始化和 Web。

公开请求的数据流：

```text
浏览器 -> Django 中间件 -> 公开视图 -> 表单校验
       -> selector/queryset -> PostgreSQL -> Django 模板
```

用户和后台的数据流：

```text
普通用户 -> 前台登录 -> 公开浏览
管理员   -> 前台登录 -> 导航显示管理入口 -> Django Admin
         -> 管理用户/栏目/文章 -> Django LogEntry
```

## 5. 数据模型

### 5.1 核心表

#### `auth_user`

沿用 Django 内置用户表。角色不增加重复字段：

- 普通用户：`is_superuser=False`、`is_staff=False`。
- 管理员：`is_superuser=True`、`is_staff=True`。
- 禁用用户：`is_active=False`。

管理员在后台切换角色时必须同步设置 `is_superuser` 和 `is_staff`，避免出现后台可进入但不具备管理员角色，或拥有超级权限但入口不可见的中间状态。

#### `content_category`

- `id`：`BigAutoField` 主键。
- `name`：最长 50 字符，唯一，非空。
- `description`：栏目简介，可为空。
- `created_at`：带时区创建时间。

#### `content_item`

- `id`：`BigAutoField` 主键。
- `title`：最长 200 字符，非空且不能只包含空白。
- `content`：完整正文，非空且不能只包含空白。
- `category_id`：栏目外键，`PROTECT` 删除策略。
- `author_id`：用户外键，可空，用户删除时 `SET_NULL`。
- `publish_time`：带时区发表时间。
- `updated_at`：带时区最后修改时间。
- `is_published`：发布状态，默认 `False`。新文章必须由管理员明确发布。

栏目与文章是一对多关系，用户与文章是可选的一对多关系。删除有文章的栏目必须失败并显示中文原因；删除作者不能删除历史文章。

### 5.2 Django 支撑表

保留 Django 自动创建的权限、用户组、用户权限关系、会话、内容类型、迁移记录和 `django_admin_log` 等表。它们是框架基础设施，不计入课程要求中的三张核心表。

### 5.3 约束和索引

- `Category.name` 使用唯一约束。
- `Item.publish_time` 使用 B-tree 索引。
- `(is_published, publish_time DESC)` 支撑首页和全部文章列表。
- `(category_id, is_published, publish_time DESC)` 支撑栏目文章列表。
- 启用 PostgreSQL `pg_trgm` 扩展。
- `Item.title` 使用 `gin_trgm_ops` GIN 索引，支撑包含式、不区分大小写的标题搜索。
- 外键和非空约束在 PostgreSQL 中执行；标题和正文的纯空白校验由 Django ModelForm 在写入边界执行，并提供中文提示。

不得仅凭 36 篇演示数据判断索引有效性。测试需要使用扩展数据和 `EXPLAIN` 验证计划。

## 6. 查询语义

前台必须支持三种独立和可组合查询模式：

1. 按文章题目：去除首尾空白后执行不区分大小写的包含查询。
2. 按发表时间：输入起止日期，按 `Asia/Shanghai` 自然日解释，两个边界均包含。
3. 按栏目：使用有效栏目主键筛选。

只查询 `is_published=True` 的文章。无条件查询返回全部已发布文章。非法日期、开始日期晚于结束日期、超过允许范围、超长关键词或非法栏目不得触发业务查询，并显示明确中文错误。搜索条件必须在分页链接中保留。

列表默认按 `publish_time DESC` 排序，并以主键作为稳定次序，防止相同时间导致跨页重复或遗漏。

## 7. 身份认证和授权

- 任何人可以匿名访问首页、栏目、文章列表、文章详情和搜索。
- 前台提供登录和退出，不提供注册入口。
- 普通用户登录后仍只能访问公开功能。
- 只有 `request.user.is_superuser` 为真时，前台导航显示“管理后台”。
- `/admin/` 使用 Django 服务端权限校验；隐藏导航不能代替授权。
- 管理员可以新增、修改、删除用户，以及在普通用户和管理员之间切换角色。
- 按已确认取舍，不保护最高管理员。任一管理员都可修改其他管理员。降级或删除管理员前提供显著确认，并在文档中说明误操作风险。
- 登录失败使用统一提示，不泄露用户名是否存在。

## 8. Django Admin

### 8.1 用户管理

- 列表展示用户名、邮箱、可见角色、启用状态和最近登录时间。
- 支持用户名和邮箱搜索，按角色和启用状态筛选。
- 创建用户时使用 Django 密码校验和哈希。
- 修改用户时通过“普通用户/管理员”抽象同步 `is_staff` 与 `is_superuser`。
- 支持启用、停用及批量角色调整。

### 8.2 栏目管理

- 支持增删改查、名称搜索和文章数聚合。
- 文章数通过单次聚合查询获得，禁止逐行计数。
- 删除有文章的栏目时显示可操作的中文提示。

### 8.3 文章管理

- 支持增删改查、标题搜索、栏目/状态/时间筛选和日期层级。
- 支持作者、栏目、发表时间、草稿和发布状态。
- 支持批量发布与撤回，并在事务提交后失效相关缓存。

### 8.4 管理操作审计

以只读列表展示 Django `LogEntry`，支持按管理员、操作类型、内容类型和时间筛选。禁止通过日志页面新增、修改或删除审计记录。

## 9. 请求和安全日志

### 9.1 记录格式

使用 UTF-8 JSON Lines。允许字段为：

- 时间、级别、日志通道和事件名。
- 请求 ID、HTTP 方法和规范化路径。
- 状态码和耗时。
- 已认证用户 ID。
- 脱敏后的 IP。

禁止记录查询字符串、请求正文、Cookie、密码、授权头、CSRF 令牌、会话标识和完整 IP。

### 9.2 保存和查看

- 日志按天轮转，保留 14 天。
- Compose 使用持久化日志卷。
- 控制台仍输出适合容器采集的结构化日志。
- Django Admin 提供只读日志页面，按日期、级别、事件、状态码和请求 ID 筛选并分页。
- 页面只读取有界数量的近期记录，不能一次加载全部日志。
- 文件不存在时显示“暂无可用日志”；损坏行跳过并记录告警，后台不能崩溃。

管理操作审计继续保存在 PostgreSQL，且不自动清理。

## 10. 前台视觉设计

前台以 2026-08-14 实际检查的 `https://www.bjtu.edu.cn/` 为唯一视觉基准：

- 顶部品牌区背景 `#005bac`，桌面高度约 90px。
- 使用本地化的官网 228 x 61 校名标识。
- 主导航高度 46px，白色 16px/700 文字。
- 正文默认 14px、`#333`。
- 字体栈以 `Microsoft YaHei`、宋体、黑体和常见无衬线字体为主。
- 内容区最大宽度 1200px。
- 分区标题主要使用 20px/700 中英组合形式。
- 页脚背景 `#065eb1`，白色 14px 信息文字。
- 响应式节点参考 1386px、992px、767px 和 480px。

### 10.1 页面结构

- 首页：品牌区、功能导航、全宽校园图片轮播、交大头条、教学科研、校园动态、通知公告、校园影像和专题栏目。
- 文章列表：官网式分区标题、双列信息节奏、栏目筛选和分页。
- 搜索页：标题、日期和栏目集中查询，结果复用文章列表。
- 文章详情：窄阅读栏，展示标题、栏目、作者、时间和正文。
- 登录页：使用相同品牌头和页脚，不显示注册入口。
- 后台：使用校名标识、蓝色页头、字体和主题色，保留 Django Admin 的高密度表格和表单。

导航功能项为首页、栏目、文章和查询。右侧显示登录或退出；管理员额外显示管理后台入口。

### 10.2 素材和声明

- 官网素材下载到项目静态目录，运行时不访问官网资源。
- 来源清单记录原始 URL、抓取日期、用途和许可说明。
- 图片添加有意义的 `alt`。
- 页脚可保留学校地址和邮编，但不得冒用官网 ICP 备案主体或官方网站版权声明。
- 页脚明确显示“课程 CMS 原型，非官方网站”和素材来源入口。

### 10.3 可访问性和响应式

- 移动端折叠导航，不允许页面级横向滚动。
- 轮播可用键盘控制并提供暂停，尊重 `prefers-reduced-motion`。
- 当前导航、焦点、错误和发布状态不能只依赖颜色表达。
- 正文和交互控件满足 WCAG 2.2 AA 基础对比度和键盘操作要求。

## 11. 初始化数据

幂等管理命令生成：

- 8 个栏目：交大头条、通知公告、教学科研、校园动态、招生就业、学术活动、国际交流、信息公开。
- 36 篇原创完整文章，时间覆盖多个年份和月份，其中 3 篇为草稿。
- 2 个普通用户和 2 个管理员。

固定演示用户名为普通用户 `student`、`visitor` 和管理员 `cms_admin`、`content_admin`。普通用户密码读取 `DEMO_USER_PASSWORD`，管理员密码读取 `DEMO_ADMIN_PASSWORD`；缺少任一变量时初始化命令明确失败，不生成已知默认密码。用户名可以写入文档，密码不得写入 Git、固定源码或文档。

数据必须覆盖标题、日期和栏目三种查询的稳定演示场景。重复执行使用栏目名、文章固定标识和用户名等稳定自然键更新或跳过，不生成重复记录。命令输出创建、更新、跳过和草稿数量。

## 12. PostgreSQL 18 迁移

### 12.1 删除旧后端

- 删除 PyMySQL 依赖和 `install_as_MySQLdb()`。
- 删除 MySQL 引擎、端口、字符集和 SQL mode 配置。
- 删除 SQLite 运行及测试分支。
- 删除 Compose MySQL 服务、健康检查和 `mysql-data` 卷。
- 删除 README、部署文档、BAT 和示例环境中的 MySQL/SQLite 说明。

### 12.2 新后端

- 使用 Django PostgreSQL 后端和当前兼容的 Psycopg 3。
- 环境变量统一为 `POSTGRES_DB`、`POSTGRES_USER`、`POSTGRES_PASSWORD`、`POSTGRES_HOST` 和 `POSTGRES_PORT`。
- Compose 使用 `postgres:18` 和新的 `postgres-data` 卷。
- 设置连接健康检查、有限连接复用和连接超时。
- Compose 使用 UTF-8 编码、`C.UTF-8` locale 和 `Asia/Shanghai` 应用时区；测试不得依赖数据库区域设置产生的隐式中文排序。原生部署使用操作系统可用的 UTF-8 locale，并保持相同查询语义。
- 测试使用独立 PostgreSQL 测试数据库或隔离的 Compose 测试服务。

这是重建迁移，不提供旧数据导入或双写。文档必须明确旧 MySQL 卷不会自动转换，并提供用户主动清理旧卷的命令和风险提示。

## 13. 部署与启动

标准流程：

```text
docker compose up --build --wait
  -> PostgreSQL 18 健康
  -> Redis 健康
  -> 执行 Django 迁移
  -> 初始化演示数据
  -> 收集静态资源
  -> Waitress 启动
  -> readiness 检查通过
```

Windows BAT 检查 Docker 可用性后调用 Compose，不自行维护另一套数据库生命周期。文档另提供原生 PostgreSQL 手动部署、迁移、初始化、创建测试数据库、运行测试和启动 Waitress 的步骤。

敏感环境变量不得进入 Git。`.env.example` 仅提供变量名和不可用的替换提示。

## 14. 异常和降级

- PostgreSQL 不可用时 readiness 失败，迁移和 Web 启动不能伪装成功。
- Redis 不可用时公开浏览降级为无缓存；公网后台登录限流保持失败关闭。
- 非法搜索输入不执行业务查询。
- 草稿和不存在文章对前台统一返回 404。
- 非管理员访问后台进入登录流程或返回 403。
- 管理写操作由数据库事务保护，缓存只在提交后失效。
- 日志文件缺失或含损坏行时日志页降级显示，不影响内容管理。

## 15. 测试和质量门禁

### 15.1 自动化测试

- 模型约束、索引声明、栏目保护删除和作者删除保留文章。
- 草稿在首页、列表、搜索和详情中不可见。
- 三种独立查询、组合查询、日期边界和稳定分页。
- 非法日期、范围、关键词、栏目和页码。
- 匿名、普通用户和管理员的登录、导航与后台权限。
- 用户、栏目、文章 CRUD、角色切换和批量发布。
- 管理操作审计生成及只读限制。
- 请求日志脱敏、轮转、筛选、分页和损坏行容错。
- 初始化命令幂等性。
- PostgreSQL、Redis、Web 健康检查与降级。

### 15.2 静态和数据库验证

- 所有修改过的 Python 文件通过 BasedPyright LSP 诊断。
- Ruff 检查 PEP 8、导入顺序和常见错误。
- Django 完整测试通过。
- `makemigrations --check` 无未提交迁移。
- `manage.py check` 和生产配置检查通过。
- 首页、栏目列表和搜索使用查询次数断言防止 N+1。
- 扩展数据下使用 PostgreSQL `EXPLAIN` 验证预期索引。

### 15.3 浏览器验收

使用 Playwright 在桌面、平板和手机视口验证：

- 首页、栏目、文章列表、详情和三种搜索。
- 普通用户登录后无后台入口且无法进入后台。
- 管理员登录后出现后台入口并可完成用户、栏目、文章 CRUD。
- 审计和请求日志页面可筛选且无敏感信息。
- 官网素材本地加载，布局无重叠、溢出或空白图片。

### 15.4 干净环境验收

必须从全新 Compose 卷完成构建、迁移、连续两次初始化、完整测试、前后台操作和日志检查。只在开发者已有数据库上运行不算通过。

## 17. 验收标准

完成必须同时满足：

1. 仓库不再含 MySQL、PyMySQL 或 SQLite 运行/测试路径。
2. 本地、Compose 和测试全部使用 PostgreSQL 18。
