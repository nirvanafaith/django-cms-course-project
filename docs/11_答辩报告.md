# 基于 Python/Django 的 CMS 原型系统答辩报告

> 本报告依据当前仓库最终代码编写。项目实际运行环境为 Python 3.12.9、Django 5.2.17 和 SQLite。重构后的自动化测试实际执行 86 项，全部通过。

## 1. 项目概述

### 1.1 项目要解决的问题

本项目是一个校园内容管理系统，也可以理解为一个小型校园新闻和通知网站。系统把校园内容分成“栏目”和“文章”两类对象：栏目类似文件夹，文章类似文件夹中的具体文件。管理员可以在后台创建栏目、发布文章、修改文章和删除文章；普通访问者不需要登录即可浏览已经发布的内容，并且可以按标题关键词、发表日期和栏目进行查询。

项目包含两个角色：

| 角色 | 可以做什么 |
| --- | --- |
| 普通用户 | 查看首页、栏目列表、文章详情、搜索文章和翻页 |
| 管理员 | 登录 Django Admin，管理栏目和文章，批量发布或撤回文章 |

草稿是系统中的一个重要业务规则。文章保存后可以处于“已发布”或“草稿”状态。草稿仍然保存在数据库中，管理员可以看到，但是普通用户通过前台任何入口都看不到草稿，直接访问草稿编号也会得到 404 页面。

### 1.2 功能清单

1. 首页展示栏目导航和最新 8 篇已发布文章。
2. 文章列表页支持按栏目筛选和分页。
3. 文章详情页只展示已发布文章。
4. 搜索页支持标题关键词、开始日期、结束日期、栏目四种条件。
5. 多个查询条件同时出现时使用 AND 语义，即必须同时满足所有条件。
6. 非法日期、非法栏目和错误页码不会导致服务器崩溃。
7. Admin 提供栏目和文章 CRUD，文章支持批量发布和批量撤回。
8. `python manage.py seed_data` 生成可重复的演示数据。

## 2. 给初学者的 Web 基础

### 2.1 浏览器、URL 和 HTTP

浏览器是用户看到网页的程序。用户在地址栏输入 `http://127.0.0.1:8000/search/` 时，浏览器会向本机的 8000 端口发送 HTTP 请求。HTTP 请求中包含方法、路径和查询参数。

- `GET /`：请求首页。
- `GET /search/?q=Python`：请求搜索页，并把 `q=Python` 作为查询参数。
- `GET /item/12/`：请求编号为 12 的文章详情。
- HTTP 200：请求成功。
- HTTP 302：重定向，例如后台未登录时跳转到登录页。
- HTTP 404：资源不存在，或系统有意隐藏它，例如草稿文章。
- HTTP 403：服务器理解请求，但拒绝访问，例如没有权限的用户访问后台。

服务器收到请求后生成 HTTP 响应。响应通常包含状态码、HTML 页面、CSS、JavaScript 和其他浏览器需要的资源。

### 2.2 Django 是什么

Django 是 Python 的 Web 框架。框架可以理解为一套已经搭好的房屋结构，开发者只需要按照约定填写路由、模型、表单、视图和模板，而不必从零实现 HTTP 解析、数据库连接、用户登录、CSRF 防护和后台管理。

本项目使用 Django 的 MVT 思想：

- Model：模型，负责描述数据库中的对象和字段。
- View：视图，负责处理一次请求并返回响应。
- Template：模板，负责把视图提供的数据变成 HTML。

本项目在 Django MVT 上增加了两个明确的内部模块：`selectors.py` 负责只读查询，`pagination.py` 负责分页工具。它们不是额外的框架，而是为了让现有代码更高内聚、低耦合。

## 4. 模块化架构

### 4.1 依赖方向

```text
浏览器
  ↓
config.urls / content.urls
  ↓
content.views
  ├── content.forms
  ├── content.selectors ── content.models ── Django ORM ── SQLite
  └── content.pagination
  ↓
templates
```

`models.py` 不导入 `views.py`，`selectors.py` 不接收 `HttpRequest`，`pagination.py` 不知道文章是什么，模板不直接调用 ORM。上层只通过参数和返回值使用下层，这种依赖方向可以避免循环依赖。

### 4.2 为什么这样高内聚

高内聚表示一个模块内部的代码都围绕同一个主题。当前模块的主题如下：

| 文件 | 单一职责 |
| --- | --- |
| `models.py` | 描述数据库实体、约束和文章可见性查询集合 |
| `forms.py` | 把不可信的 GET 字符串解析为合法的 Python 值 |
| `selectors.py` | 构造前台只读查询 |
| `pagination.py` | 统一分页规则和翻页参数 |
| `views.py` | 编排一次 HTTP 请求到响应的流程 |
| `admin.py` | 声明 Django 后台的列表、过滤和批量操作 |
| 模板 | 展示视图上下文 |

如果搜索条件改变，主要修改表单和 selector；如果每页数量改变，主要修改 pagination；如果 URL 或页面上下文改变，修改 view。一个模块不会因为另一个完全不同的原因而频繁变化。

### 4.3 为什么这样低耦合

低耦合表示模块之间依赖少、依赖稳定。比如 `search()` 不再知道“结束日期要加一天”，它只把表单清洗后的 `date` 传给 `search_published_items()`。以后日期规则变化时，视图不需要跟着修改。

这里使用的是数据耦合：模块通过 `Category`、`QuerySet`、`date` 和 `Page` 等数据交换信息，而不是互相修改内部变量或依赖对方的实现细节。

## 5. 逐文件说明

### 5.1 `cms_site/manage.py`

`manage.py` 是命令行入口。运行 `python manage.py test`、`python manage.py migrate`、`python manage.py seed_data` 或 `python manage.py runserver` 时，操作系统都会先执行这个文件。

导入项：

- `os`：设置环境变量 `DJANGO_SETTINGS_MODULE`。
- `sys`：读取命令行参数 `sys.argv`。

函数 `main()`：

1. 使用 `os.environ.setdefault()` 指定配置模块为 `config.settings`。
2. 在函数内部导入 `execute_from_command_line`，避免在 Django 配置尚未准备好时过早加载框架。
3. 如果 Django 没安装，抛出带有环境提示的 `ImportError`。
4. 把 `sys.argv` 交给 Django 的命令分发系统。

变量 `application` 不在本文件中出现，因为命令行文件和部署入口的职责不同。

### 5.2 `config/settings.py`

这是整个项目的配置中心。

- `BASE_DIR`：通过 `Path(__file__).resolve()` 找到配置文件位置，再向上定位项目目录。数据库、模板、静态文件都以它为基础拼接路径。
- `SECRET_KEY`：Django 用于签名 Cookie 和安全令牌。生产环境可以由 `DJANGO_SECRET_KEY` 环境变量提供。
- `DEBUG`：由 `DJANGO_DEBUG` 控制。开发时显示调试信息，生产时应关闭。
- `ALLOWED_HOSTS`：允许访问本项目的主机名列表。
- `INSTALLED_APPS`：注册 Django Admin、认证、会话、静态文件和 `content` 应用。
- `MIDDLEWARE`：请求经过的中间件链。安全、会话、CSRF、认证和消息等能力都在这里启用。
- `ROOT_URLCONF`：项目总路由模块名。
- `TEMPLATES`：配置模板引擎、项目级 `templates` 目录、应用内模板发现和上下文处理器。
- `DATABASES`：默认使用 SQLite；当 `DB_ENGINE=mysql` 时读取 MySQL 环境变量。
- `LANGUAGE_CODE` 和 `TIME_ZONE`：控制中文显示和上海时区。
- `USE_TZ=True`：让数据库时间带有时区语义。
- `STATIC_URL`、`STATICFILES_DIRS`、`STATIC_ROOT`：分别是静态 URL、开发静态目录和生产收集目录。
- `SESSION_COOKIE_HTTPONLY`、`SESSION_COOKIE_SAMESITE`、`CSRF_COOKIE_HTTPONLY`：降低会话和跨站请求风险。
- `LOGGING`：定义控制台和滚动文件日志。
- `DEFAULT_AUTO_FIELD`：新模型默认使用 64 位自增主键。

### 5.3 `config/urls.py`

`urlpatterns` 是项目级路由表。`path("admin/", admin.site.urls)` 把 `/admin/` 交给 Django Admin，`include("content.urls")` 把根路径交给业务应用。最后三行设置后台标题、浏览器标题和首页标题。

### 5.4 `config/wsgi.py` 与 `config/asgi.py`

两者都设置 `DJANGO_SETTINGS_MODULE` 并创建名为 `application` 的对象。WSGI 适合传统同步服务器，ASGI 是更现代的异步服务器接口。普通开发通过 `runserver` 启动，部署工具可以导入 `config.wsgi:application` 或 `config.asgi:application`。

### 5.5 `content/apps.py`

`ContentConfig` 告诉 Django：应用名称是 `content`，默认主键类型是 `BigAutoField`。Django 启动时依据这个配置发现模型、Admin、迁移和 management command。

### 5.6 `content/models.py`

#### `ItemQuerySet`

`ItemQuerySet` 继承 Django `models.QuerySet`。它增加一个 `published()` 方法：

```python
Item.objects.published()
```

等价于构造 `is_published=True` 的过滤条件，但比在四个视图中重复写条件更集中。`filter()` 返回新的 QuerySet，仍然可以继续 `.select_related()`、`.filter()` 和 `.order_by()`。QuerySet 是惰性的，构造对象不等于立刻查数据库，真正遍历或执行 `exists()` 时才查询。

#### `Category`

字段说明：

- `name`：最多 50 个字符，唯一，作为栏目名称。
- `description`：栏目简介，`blank=True` 允许表单为空，`null=True` 允许数据库为空。
- `created_at`：创建时自动填写，Admin 中只读。

`Meta.ordering = ("id",)` 让栏目默认按主键升序排列。`__str__()` 返回 `name`，因此下拉框和 Admin 列表显示栏目名称而不是 `Category object (1)`。

#### `Item`

- `objects`：使用 `ItemQuerySet.as_manager()` 把 `published()` 暴露到模型管理器。
- `title`：最多 200 个字符，是标题查询字段。
- `content`：正文，允许空字符串。
- `category`：指向 `Category` 的外键。`PROTECT` 表示栏目被文章引用时不能删除。
- `publish_time`：发表时间，默认当前时间，并用 `db_index=True` 支持时间范围查询。
- `updated_at`：修改时自动更新，Admin 中只读。
- `is_published`：发布开关，默认 `True`。
- `author`：可选的 Django 用户外键。作者删除后文章保留，作者值改为 `NULL`，因为使用 `SET_NULL`。

`Meta.ordering = ("-publish_time",)` 让文章默认按最新时间在前。`__str__()` 返回标题。

### 5.7 `content/forms.py`

`SearchForm` 是用户输入边界。浏览器提交的 GET 参数本质上都是字符串，表单负责把字符串解析成更可靠的内部数据。

- `q`：可选标题关键词，最多 100 个字符，`strip=True` 删除首尾空格。
- `start`：可选开始日期，只接受 `%Y-%m-%d`。
- `end`：可选结束日期，只接受 `%Y-%m-%d`。
- `category`：`ModelChoiceField`，使用 `Category.objects.all()` 作为选项来源，把合法主键转换为 `Category` 对象。

`clean_q()` 把空字符串统一转换为 `None`，方便 selector 判断“有没有关键词”。`clean()` 读取 `start` 和 `end`，如果开始日期晚于结束日期，就通过 `add_error(None, ...)` 增加表单级错误。

### 5.8 `content/selectors.py`

该文件只负责只读 ORM 查询。

- `_aware_midnight(day)`：把 Python `date` 组合成当天零点，再用 Django 当前时区转换为 aware datetime。
- `categories_with_item_counts()`：使用 `Count("items", filter=Q(items__is_published=True))`，只计算前台能看到的文章数量。
- `latest_published_items(limit=8)`：调用 `published()` 过滤草稿，调用 `select_related("category")` 预加载栏目，并切片限制数量。
- `published_items_for_category(category_id=None)`：先取所有已发布文章，有栏目主键时再按外键过滤。
- `published_item_by_pk(pk)`：读取一篇已发布文章。不存在或草稿时抛出 `Item.DoesNotExist`，HTTP 转换由 view 完成。
- `search_published_items(...)`：逐项追加关键词、开始日期、结束日期和栏目条件，天然形成 AND 查询。

`end` 使用“下一天零点之前”的开区间。例如用户输入 2026-08-08，内部条件是 `publish_time < 2026-08-09 00:00:00`，所以 8 月 8 日 18:00 的文章不会被漏掉。

### 5.9 `content/pagination.py`

- `PAGE_SIZE`：常量 10，表示列表页每页十篇。
- `paginate(items, page_number)`：创建 Django `Paginator` 并调用 `get_page()`。非整数或小于 1 时回到第一页，超出范围时回到末页。
- `query_without_page(query_params)`：复制不可变的 `QueryDict`，删除旧的 `page`，再调用 `urlencode()`。这样分页模板可以追加新的 `page`，不会产生 `page=1&page=2`。

### 5.10 `content/views.py`

四个 view 都接收 `HttpRequest` 并返回 `HttpResponse`。

- `index(request)`：调用两个 selector，构造 `categories`、`latest_items`、`page_title` 上下文，渲染 `content/index.html`。
- `item_list(request)`：读取 `category` 和 `page`，查询当前栏目对象，调用 `published_items_for_category()` 与 `paginate()`，渲染列表模板。
- `item_detail(request, pk)`：调用 `published_item_by_pk()`。只捕获明确预期的 `Item.DoesNotExist`，转换为 `Http404`，不泄露草稿存在性。
- `search(request)`：创建并校验 `SearchForm`。成功时取 `cleaned_data` 传给 selector；失败时使用 `Item.objects.none()`，只显示错误而不执行无效查询；最后调用分页工具和模板。

重要局部变量：`form` 是表单对象，`cleaned` 是清洗后的可信数据，`current_category` 是当前栏目，`items` 是 QuerySet，`context` 是传给模板的变量字典。

### 5.11 `content/admin.py`

`@admin.register(Category)` 和 `@admin.register(Item)` 是 Django 注册装饰器。`CategoryAdmin` 设置栏目列表列、名称搜索、创建时间只读和排序；`get_queryset()` 使用 `annotate(_item_count=Count("items"))`，避免每行重复 Count 查询；`article_count()` 读取已注解的值。

`ItemAdmin` 设置标题、栏目、时间和发布状态列，增加状态/栏目/日期过滤、标题搜索、日期层级、每页 20 条和更新时间只读。`mark_published()`、`mark_draft()` 使用 QuerySet `update()` 一次批量修改所有选中行，并用 `message_user()` 给管理员反馈数量。

### 5.12 `seed_data.py`

`CATEGORIES` 是栏目定义表，每个元组包含名称、简介和文章数，总共 63 篇。`KEYWORDS` 保证标题包含可用于答辩演示的关键词。`TIME_START` 和 `TIME_END` 是上海时区的时间边界，`RANDOM_SEED` 保证随机结果可复现。

`Command.handle()` 先用 `Category.objects.exists()` 判断是否已有演示数据，保证重复执行不会重复插入。`rng` 是固定种子的随机数生成器，`total_items` 统计当前生成数量，`draft_count` 表示前三篇设置为草稿，`name`、`desc`、`count` 分别来自栏目定义，`i` 是栏目内序号，`kw` 是随机关键词，`delta` 是随机时间偏移，`cat` 是栏目对象，`is_published` 是发布状态。

`_content(cat_name, keyword)` 依据栏目和关键词生成没有真实个人信息的演示正文。

## 6. 模板和静态文件

### 6.1 HTML 模板

- `templates/base.html`：所有页面的骨架，加载 static 标签、Bootstrap CDN、设计令牌和自定义 CSS，包含导航、消息区、主内容块、页脚和延迟加载的 JavaScript。
- `templates/partials/nav.html`：导航栏和移动端菜单按钮。
- `templates/partials/messages.html`：显示 Django message framework 消息。
- `templates/partials/pagination.html`：显示上一页、下一页、页码和结果总页数。
- `templates/content/index.html`：继承基模板，显示欢迎区、栏目入口和最新文章。
- `templates/content/item_list.html`：同时承担栏目列表和搜索结果列表，包含条件摘要、结果数、空状态和分页。
- `templates/content/search_form.html`：展示 q/start/end/category 四个查询字段、帮助文字和错误。
- `templates/content/item_detail.html`：显示面包屑、栏目、标题、时间、作者、正文和返回栏目按钮。
- `templates/admin/base_site.html`：覆盖 Django Admin 基模板入口，接入项目视觉样式但保留 Admin 原生功能。

模板使用 `{% url %}` 反向解析命名路由，避免把 URL 字符串散落在 HTML 中。Django 默认开启 autoescape，文章标题、正文和用户可控内容会被转义，从而降低 XSS 风险。`csrf_token` 保护后台 POST 表单。

### 6.2 CSS 与 JavaScript

`static/css/tokens.css` 是视觉令牌文件，集中保存背景、表面、边框、文字、动作色、字号、间距、圆角和动效时间。修改令牌可以整体调整视觉，而不需要逐个寻找颜色。

`static/css/custom.css` 使用这些令牌定义导航、按钮、栏目入口、文章列表、搜索面板、错误提示、分页、面包屑和文章阅读区，并通过媒体查询适配窄屏。

`static/css/admin.css` 只做 Django Admin 的视觉覆盖，不重写后台权限、表单提交和 CRUD 逻辑。

`static/js/main.js` 是一个很小的原生脚本。它找到 `[data-nav-toggle]` 和 `[data-nav-menu]`，点击按钮时同步更新 `aria-expanded`、`aria-label` 和 `is-open` CSS 类。它不负责业务数据，也不访问数据库。

## 7. 第三方库与 API 科普

## 8. 三条核心流程

### 8.1 浏览首页

1. 浏览器请求 `/`。
2. `config.urls` 把根路径 include 到 `content.urls`。
3. `content.urls` 找到 `views.index`。
4. `index()` 调用 `categories_with_item_counts()` 和 `latest_published_items()`。
5. selector 通过 ORM 生成参数化 SQL。
6. `render()` 把栏目和文章放入模板上下文。
7. `index.html` 继承 `base.html`，生成最终 HTML。

### 8.2 组合搜索

1. 浏览器访问 `/search/?q=Python&start=2026-08-01&end=2026-08-31&category=2`。
2. `SearchForm` 读取四个字段。
3. `CharField` 清理关键词，`DateField` 清理日期，`ModelChoiceField` 查询并验证栏目。
4. 如果校验失败，使用 `Item.objects.none()`，页面返回 200 并展示错误。
5. 如果校验成功，`search_published_items()` 先排除草稿，再逐项增加 AND 条件。
6. 结束日期被转换为下一天零点的开区间上界。
7. `paginate()` 使用每页 10 条的 `Paginator`。
8. `query_without_page()` 保留 q、start、end、category，分页模板再追加当前页码。
9. 模板展示结果或空状态。

### 8.3 管理员发布文章

1. 管理员访问 `/admin/`。
2. Django Admin 通过认证和 `is_staff` 判断是否允许进入。
3. 管理员在文章表单填写标题、正文、栏目、时间和发布状态。
4. Django ORM 保存 `Item`。
5. 前台页面通过 `Item.objects.published()` 读取文章。
6. 若状态为已发布，文章出现在首页、列表、详情和搜索；若状态为草稿，所有前台入口都隐藏它。
7. 管理员也可以用 `mark_published` 或 `mark_draft` 批量切换状态。

## 9. 数据库与规范化

### 9.1 表关系

一个 `Category` 可以包含多篇 `Item`，一篇 `Item` 必须属于一个 `Category`。`Item.author` 是可选的 Django 用户关系。文章表不复制栏目名称，而是保存 `category_id` 外键，因此栏目名称只在栏目表中维护。

### 9.2 BCNF 答辩说法

`Category` 的主键是 `id`，表内依赖可以写成 `id → name, description, created_at`。`Item` 的主键也是 `id`，依赖可以写成 `id → title, content, category_id, publish_time, updated_at, is_published, author_id`。每一个非平凡函数依赖的决定因素都是候选键或超键，因此两张作业核心表满足 BCNF。

`category_id → Category.name` 是跨表外键关联，不是 `Item` 表内部的函数依赖。`PROTECT` 是数据完整性策略，不改变规范化证明。

## 10. 安全、性能和可维护性

### 10.1 安全

- SQL 注入：只使用 Django ORM 参数化查询，不拼接 SQL 字符串。
- XSS：模板默认 autoescape，不使用不安全的 `safe` 过滤器显示正文。
- CSRF：Django CSRF 中间件和模板 token 保护 POST。
- 越权：Admin 由 Django 认证和 `is_staff` 控制，前台 selector 过滤草稿。
- Cookie：启用 HttpOnly 和 SameSite=Lax。
- 密钥：生产环境通过环境变量设置 `DJANGO_SECRET_KEY`。
- 错误信息：草稿和不存在文章都使用 404，避免泄露草稿主键存在性。

### 10.2 性能

- `publish_time` 有数据库索引，时间范围查询可以利用索引。
- 外键过滤使用 `category_id`，避免加载无关对象。
- `select_related("category")` 把文章和栏目读取合并到一次 JOIN。
- 标题 `icontains` 是任意子串匹配，通常需要线性扫描；在本项目演示规模内可以接受，未来数据量巨大时再考虑全文索引。
- `Paginator` 使用数据库分页语义，但深页仍有 OFFSET 跳过成本。

### 10.3 维护性

核心维护原则是单一职责、DRY、YAGNI 和依赖方向清晰。当前项目没有引入 Repository、Service、REST API 或前端 SPA，因为这里只有两个实体和少量页面，这些抽象没有第二个实现，反而会增加讲解成本。适度分层已经足以让查询、输入、分页和 HTTP 编排独立变化。

## 13. 常见答辩问题与回答

**问：为什么不用 React 或 Vue？**

答：本系统是内容型原型，主要交互是 GET 查询、页面回显和 Admin CRUD。Django 服务端渲染已经满足需求，引入前端框架会增加构建、状态管理和部署复杂度，但没有带来本作业需要的收益。

**问：为什么把查询从 views 拆出去？**

答：视图的职责是 HTTP 编排，查询的职责是构造 ORM QuerySet。拆出 selector 后，查询可以用真实数据库独立测试，修改日期边界或查询规则不会影响 HTTP 代码。

**问：为什么不直接使用 Repository？**

答：Repository 更适合需要替换多种存储实现的大型系统。本项目只有 Django ORM 一种持久化实现，Repository 只会包一层同样的 QuerySet，属于过度设计。当前 selector 已经实现了清晰的只读查询边界。

**问：`select_related` 解决了什么问题？**

答：文章列表要显示栏目名称。如果每篇文章单独访问 `item.category`，会先查文章，再为每篇文章查栏目，形成 1+N 次查询。`select_related` 使用 JOIN 预先把外键数据带回来，减少数据库往返。

**问：为什么结束日期要加一天？**

答：用户输入的是一个日期，通常期待看到这一天的全天内容。如果直接用当天 00:00 做 `lte`，当天 18:00 会被排除。改成“下一天 00:00 之前”，就能包含结束日期所有时刻。

**问：为什么有文章的栏目不能删除？**

答：这是内容完整性规则。`PROTECT` 防止删除后文章失去所属栏目，数据库层和 Django ORM 都会阻止这种危险操作。

**问：测试为什么不只测试函数？**

答：模型和 selector 测试关注内部规则，Client 测试关注真实 HTTP 行为，Admin 测试关注后台权限和 CRUD，安全测试关注 XSS/CSRF/越权，系统测试关注完整闭环。分层测试既定位问题快，又能验证用户真正看到的结果。

**问：项目哪里体现高内聚低耦合？**

答：表单只做输入解析，selector 只做只读查询，pagination 只做分页，view 只做请求响应编排，模板只做展示。模块通过稳定的数据契约连接，且 models 不反向依赖上层，因此满足高内聚低耦合。

**问：如果数据量扩大怎么办？**

答：可以先把 SQLite 换成 MySQL，继续保留 Django ORM 接口；标题任意子串查询可迁移到 SQLite FTS5 或专业全文检索；深页分页可以改用基于游标的分页。当前原型不提前引入这些复杂度，但已经把变化点隔离出来。

## 14. 最终总结

本项目使用 Python 和 Django 完成了一个可运行的校园 CMS 原型。系统具有清晰的实体关系、完整的前台浏览与查询、Django Admin 管理能力、草稿可见性控制、参数校验、安全防护、演示数据命令和自动化测试。
