## 1. 测试目的与范围

- 验证系统满足《需求分析文档》全部 Must 需求（功能 + 非功能）；
- 验证《详细设计文档》各设计单元（模型约束、表单校验、查询组合、分页守卫、安全策略）按设计正确落地；
- 提供可执行的测试用例基线，支撑"能解释、能复现、能迭代"的课程验收要求。

**测试范围**：栏目/文章 CRUD、发布状态、前台浏览、三种查询模式、组合查询、分页、权限与安全、输入校验、演示数据、部署验收。

**不测试**：第三方库内部行为（Django/ORM 自身）、浏览器视觉像素级对比（人工抽查）、非功能压力测试（数据规模超出原型定位）。

## 2. V 模型测试策略

```
需求分析 ──┐                    ┌── 验收测试（UAT）←── 需求验收场景
概要设计 ──┤                    ├── 系统测试（端到端业务流）
详细设计 ──┼────── 编码 ────────┼── 集成测试（模块间接口/视图+ORM+模板）
          └────────────────────┘── 单元测试（最小单元：模型/表单/工具函数）
```

| 测试层级 | 被测对象 | 手段 | 执行时机 |
| --- | --- | --- | --- |
| 单元测试 | models.py 字段/方法/Meta；forms.py 校验 | Django TestCase 直测 | 每完成一个模块立即执行 |
| 集成测试 | urls→views→ORM→模板 全链路；Admin 发布→前台可见 | `Client` 模拟 HTTP | 每完成一个功能后 |
| 系统测试 | 端到端业务流（发布→查询→删除→统计） | 脚本化场景测试 | 功能冻结后全量回归 |
| 验收测试 | 需求验收脚本（助教冒烟） | 手工执行 + 文档记录 | 交付前 |

## 5. 测试用例设计方法

| 方法 | 应用 |
| --- | --- |
| 等价类划分 | 日期格式（合法 YYYY-MM-DD / 非法字符串 / 边界 2026-02-29）；标题长度（空/1/200/201） |
| 边界值分析 | 页码 1、末页、末页+1、0、-1、非数字；分页 10 条边界（10/11 条数据） |
| 错误推测 | 未登录访问管理 URL、删除被引用栏目、start>end、category=99999 |
| 状态转换 | is_published: 发布→草稿→前台消失→再发布→可见 |

## 8. 缺陷管理

### 8.1 缺陷等级

| 等级 | 定义 | 处理时限 |
| --- | --- | --- |
| A（严重） | 系统崩溃、核心功能不可用、数据丢失/损坏 | 当日修复并回归 |
| B（一般） | 功能不满足需求但可绕过、错误提示不友好 | 3 日内 |
| C（轻微） | UI 细节、文案、体验优化 | 版本内 |
| D（建议） | 改进建议（可进 Backlog） | 记录不阻塞 |

### 8.2 缺陷报告模板

```
缺陷ID：BUG-YYYYMMDD-序号     等级：A/B/C/D
标题：
复现步骤：1.  2.  3.
实际结果：
预期结果：
影响需求：FR-xxx
关联用例：T-xxx
提交人/日期：          状态：新建/已修复/已验证/关闭
```

### 8.3 缺陷处理流程

`新建 → 定位（git bisect/blame 辅助）→ 修复 → 关联用例回归 → 关闭`；修复提交需独立 commit（满足 NFR-06）。

## 9. 测试执行计划与完成标准

| 阶段 | 内容 | 时间点 |
| --- | --- | --- |
| 开发期 | 单元/集成用例随代码提交即时执行 | 每 commit 前 |
| 冻结期 | 全量回归：`python manage.py test` + 手工系统用例 | 功能冻结后 |
| 交付期 | 验收冒烟（T-ACC-*）按脚本走查 + 覆盖率统计 | 交付前 1 天 |

**出口准则（全部满足才算测试完成）**：

1. P1 用例通过率 = 100%，P2 ≥ 95%（无未修复 A 级缺陷）；
2. `python manage.py test` 全绿；
3. coverage（可选）核心模块行覆盖 ≥ 80%；
4. `ruff check` 无错误；
5. 验收冒烟 T-ACC-01~08 全部通过。

**回归策略**：任一代码变更后执行被影响模块用例 + 全量安全用例；提交前本地全量测试。
