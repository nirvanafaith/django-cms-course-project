# Django CMS 后端与数据库技术架构小白教案

> 阅读范围：本篇根据 `cms_site/config/`、`cms_site/content/`、`cms_site/core/`、迁移文件、管理命令与 Docker 配置解释实际后端实现。它面向刚接触 Web 开发、Django 和数据库的读者。

## 1. 一句话认识后端

这个项目是一个 **Django 单体应用**：公开内容、登录、管理后台、缓存、日志、健康检查和部署入口都在同一个 Python 项目里。

```text
浏览器
  -> Waitress Web 服务器
  -> Django 中间件
  -> URL 路由
  -> 视图函数
  -> 表单校验 / 查询器
  -> Django ORM
  -> PostgreSQL
  -> Django 模板生成 HTML
  -> 浏览器
```

它不是把前端和后端拆成两个独立 API 项目，也不是多个微服务。对于以文章、栏目和后台管理为核心的内容管理系统，这种结构更容易开发、调试和部署。

## 2. 项目目录如何分工

```text
cms_site/
├── manage.py                 Django 命令行入口
├── config/                   项目总配置、路由、安全、数据库和服务器入口
├── content/                  栏目与文章的业务模块
├── core/                     缓存、限流、日志、健康检查和运维能力
├── templates/                服务端渲染 HTML 模板
├── static/                   CSS、JavaScript、图片
└── Dockerfile                容器构建与启动说明
```

把它想成一个内容网站团队：

- `config` 是总控室，决定服务怎样运行。
- `content` 是内容编辑部，管理文章和栏目。
- `core` 是机房和安保部门，管理缓存、日志、权限和运行状态。

## 3. `manage.py`：Django 的命令行遥控器

`manage.py` 是常见 Django 命令的统一入口：

```bash
python manage.py migrate
python manage.py test
python manage.py collectstatic
python manage.py serve_waitress
```

它设置：

```python
DJANGO_SETTINGS_MODULE = "config.settings"
```

这告诉 Django：全局配置在 `config/settings.py`。之后 Django 的 `execute_from_command_line(sys.argv)` 根据命令行参数分发到对应命令。

## 4. WSGI、ASGI 与 Waitress

### 4.1 WSGI 是什么

**WSGI** 是 Python Web 服务器和 Web 应用之间的传统标准接口。`config/wsgi.py` 生成：

```python
application = get_wsgi_application()
```

这个 `application` 是 Waitress 调用的 Django 应用对象。

### 4.2 Waitress 做什么

Waitress 是第三方 WSGI 服务器。管理命令 `serve_waitress` 调用它监听主机和端口，再将每个 HTTP 请求交给 Django。

它配置了：

- 线程数。
- 最大连接数与排队长度。
- 请求头和请求体大小上限。
- 连接超时。
- 可信代理头。
- 不向浏览器暴露 Python traceback。

这些设置不是页面功能，却能防止单个异常请求无限占用资源，或把内部报错细节直接泄露给访问者。

### 4.3 ASGI 为什么也存在

`config/asgi.py` 也生成 ASGI 应用。ASGI 更适合异步长连接、WebSocket 等场景。当前项目主要走 Waitress + WSGI，但保留 ASGI 入口，让未来部署到 ASGI 服务器时仍有标准接口。

## 5. 请求怎样抵达一个页面

用户访问：

```text
/search/?q=校园
```

大致过程是：

```text
1. Waitress 接收 HTTP 请求
2. Django 依序执行中间件
3. config.urls 找到 content.urls
4. content.urls 将 /search/ 指到 content.views.search
5. search 创建 SearchForm 校验 URL 参数
6. selectors.search_published_items 组装 ORM 查询
7. PostgreSQL 返回文章记录
8. Paginator 切出当前页
9. render 让模板生成 HTML 响应
```

## 6. 路由：网址的接线表

`config/urls.py` 是根路由表。它将不同网址前缀交给不同模块：

```text
/admin/                 Django Admin
/accounts/login/        Django 内置登录视图
/accounts/logout/       Django 内置退出视图
/health/                健康检查
/                       content 应用的公开页面
```

`content/urls.py` 再定义公开内容路由：

```text
/                 首页
/item/<int:pk>/   文章详情
/search/          搜索与分页
```

其中 `<int:pk>` 表示 URL 中的一段必须是整数，并传给视图函数。`pk` 是 primary key（主键）的常用缩写，也就是文章在数据库中的唯一编号。

## 7. 视图：一次请求的编排者

`content/views.py` 的视图函数处理 HTTP 请求，但不会把所有工作塞在同一个文件。

它的职责是：

1. 读取 `HttpRequest`。
2. 调用表单校验输入。
3. 调用查询器取得数据。
4. 调用分页工具。
5. 组装模板 context。
6. 通过 `render()` 返回 HTML。

这种分层很重要：

```text
views.py        HTTP 请求和响应流程
forms.py        用户输入的格式与业务校验
selectors.py    只读 ORM 查询
pagination.py   分页与 URL 参数处理
models.py       数据库结构
```

### 7.1 首页

首页调用 `homepage_items()`，最多读取 24 篇公开文章。它把文章按栏目名分组，再交给首页模板。

如果公开页面缓存开启，首页先尝试从缓存读取；缓存未命中才读数据库。

### 7.2 文章详情

详情页只按“主键 + 已发布状态”查文章。草稿和根本不存在的文章都会变成 404：

```text
访客看不到草稿是否真实存在
```

这比“模板里不显示草稿”更可靠，因为数据库查询本身就把草稿排除了。

### 7.3 搜索

搜索页先创建 `SearchForm(request.GET)`。只有 `form.is_valid()` 成功后才查询数据库；错误输入不会直接进入查询条件。

## 8. 表单：浏览器输入的第一道边界

`content/forms.py` 中的 `SearchForm` 使用 Django `forms.Form`。

Django 表单可以：

- 从 GET/POST 读取字符串。
- 将日期文本转换成 Python `date` 对象。
- 验证最大长度、选项范围和日期格式。
- 保存错误信息，供模板显示。

搜索可接受：

```text
q         标题关键词
start     开始日期
end       结束日期
category  栏目
```

额外规则包括：

```text
开始日期不能晚于结束日期
日期区间不能超过 366 天
```

这说明输入校验不只检查每个字段本身，也会检查字段之间的关系。

前端 HTML 限制只能改善体验；真正的安全边界必须在服务器端，所以 Django Form 仍然必不可少。

## 9. PostgreSQL：业务数据真正保存在哪里

项目通过 `config/backends.py` 只配置 PostgreSQL：

```python
"ENGINE": "django.db.backends.postgresql"
```

启动需要：

```text
POSTGRES_DB
POSTGRES_USER
POSTGRES_PASSWORD
```

可选配置包括：

```text
POSTGRES_HOST，默认 127.0.0.1
POSTGRES_PORT，默认 5432
```

还设置了：

- 连接复用最多 60 秒。
- 复用前健康检查。
- 连接超时 5 秒。

`verify_postgres` 管理命令还要求运行的数据库确实是 PostgreSQL，并且版本不低于 18。

## 10. ORM：用 Python 描述表，而不是手写大部分 SQL

**ORM** 是 Object-Relational Mapping 的缩写，可以理解为“Python 对象和关系型数据库表之间的翻译层”。

例如：

```python
Item.objects.filter(is_published=True)
```

Django 会把它翻译成大致对应的 SQL：

```sql
SELECT ...
FROM content_item
WHERE is_published = true;
```

开发者仍要理解数据库行为，但不必把每个普通查询拼成字符串 SQL。

## 11. 两个核心模型：栏目和文章

数据库模型在 `content/models.py`。

### 11.1 `Category`：栏目

概念上相当于：

```text
Category
├── id            自动主键
├── name          栏目名称，必须唯一
├── description   栏目简介，可为空
└── created_at    创建时间
```

`unique=True` 表示数据库不允许两个同名栏目。

### 11.2 `Item`：文章

```text
Item
├── id             自动主键
├── title          标题
├── content        正文
├── category_id    所属栏目
├── publish_time   发布时间
├── updated_at     最后修改时间
├── is_published   是否公开
└── author_id      作者用户
```

每一个 `Item` 对象对应文章表的一行。

## 12. 外键：表之间怎样关联

### 12.1 一篇文章属于一个栏目

```python
category = models.ForeignKey(Category, on_delete=models.PROTECT)
```

这代表多对一关系：

```text
一个栏目 -> 多篇文章
一篇文章 -> 一个栏目
```

数据库实际保存 `category_id`，不是完整栏目对象。

`PROTECT` 的意思是：只要栏目还有文章，就禁止删除栏目。这样能防止文章变成没有所属栏目的孤儿数据。

### 12.2 文章作者可删除，文章保留

```python
author = models.ForeignKey(..., on_delete=models.SET_NULL)
```

作者账号删除后：

```text
文章仍保留
author_id 变为 NULL
```

这是业务选择：历史内容比账号关系更需要保留。

## 13. 草稿和公开文章

新文章默认：

```python
is_published = False
```

也就是草稿。公开查询都会从：

```python
Item.objects.filter(is_published=True)
```

开始。

因此公开首页、搜索和详情都不能读取草稿。这是后端访问控制，不依赖前端“藏起来”。

`ItemQuerySet.published()` 和 `ItemManager.published()` 把这条规则封装起来，减少重复代码与漏写过滤条件的风险。

## 14. QuerySet 为什么叫“惰性查询”

下面代码通常不会立刻访问数据库：

```python
queryset = Item.objects.filter(is_published=True)
```

它只是构造查询计划。真正需要数据时，例如：

```python
list(queryset)
for item in queryset:
queryset.exists()
```

Django 才执行 SQL。

这种“惰性求值”让调用方可以不断追加条件，最后一次性发送完整查询：

```python
queryset = Item.objects.filter(is_published=True)
queryset = queryset.filter(title__icontains=keyword)
queryset = queryset.filter(category=category)
```

上面多个 `filter()` 默认以 AND 关系组合。

## 15. 查询器：把读取规则从视图中抽出来

`content/selectors.py` 只做读取：

- `homepage_items()`：公开文章、预加载关联、最多 24 条。
- `published_item_by_pk()`：按主键取一篇公开文章。
- `search_published_items()`：关键词、日期与栏目组合过滤。

它不读取 `HttpRequest`，也不决定用哪个模板或 HTTP 状态码。这样查询规则更容易复用与测试。

### 15.1 `select_related` 为什么重要

文章有栏目和作者外键。如果循环显示 10 篇文章并逐篇访问栏目，最坏情况可能产生：

```text
1 次文章查询 + 10 次栏目查询 + 更多作者查询
```

这叫 **N+1 查询问题**。

`select_related("category", "author")` 使用 SQL JOIN 一次带回多对一关联，减少额外数据库往返。

### 15.2 稳定排序

公开文章排序：

```python
.order_by("-publish_time", "-pk")
```

先按发布时间倒序，再按主键倒序。第二项的意义是：两篇文章时间完全相同时，顺序仍然确定，不会在分页时随机跳动。

### 15.3 日期范围为什么要补成时间

用户输入的是日期：

```text
2026-08-13
```

数据库保存的是完整时间。为了包含结束日期当天的全部文章，项目使用：

```text
发布时间 >= 开始日 00:00
发布时间 <  结束日下一天 00:00
```

这是常见的半开区间写法，避免把当天晚上发布的文章漏掉。

## 16. 索引：数据库的目录

索引可以想成书后的目录。没有索引时，数据库可能扫描整张文章表；合适的索引能更快找到所需记录。

`Item` 有三类关键索引：

### 16.1 公开文章的时间索引

```text
is_published + publish_time
```

服务首页“只看公开文章，按最新发布时间排序”。

### 16.2 栏目列表复合索引

```text
category + is_published + publish_time
```

服务“某栏目下的公开文章，按时间排序”。字段顺序与常见查询过滤顺序有关。

### 16.3 标题模糊搜索索引

项目启用 PostgreSQL `pg_trgm` 扩展，并使用 GIN Trigram 索引。

简单理解：文本会被拆成连续的小片段，数据库据此加速“标题中包含某段文字”的搜索。

最终索引：

```text
Upper(title)
+ 仅 is_published=True
+ gin_trgm_ops
```

只索引公开文章可以减少索引体积，也与公开搜索规则保持一致。

索引不是越多越好：每个索引会占空间，写入时也要维护。它们应围绕真实查询路径设计。

## 17. 迁移：模型变化怎样真正落到 PostgreSQL

修改 `models.py` 不会自动改变数据库。Django 用 **migration（迁移）** 记录表结构的演化。

```text
0001_initial.py
  -> 创建初始 Category 和 Item 表
0002_postgresql_constraints_indexes.py
  -> 启用 pg_trgm、调整字段、增加索引
0003_upper_title_trigram_index.py
  -> 替换标题索引为条件表达式索引
```

迁移是一串需要按顺序执行的数据库操作。不要只看 `0001` 就以为那是当前结构；当前数据库结构应理解为所有迁移依序执行后的结果。

通常通过：

```bash
python manage.py migrate
```

让 Django 执行尚未应用的迁移。

## 18. 分页：不要一次把所有文章发送到页面

`content/pagination.py` 规定：

```python
PAGE_SIZE = 10
```

`Paginator` 负责：

- 计算页数。
- 返回当前页对象。
- 告诉模板是否有上一页和下一页。
- 温和处理非法页码。

`get_page()` 对 `?page=abc` 或超出范围的页码会回退到合适页面，而不是直接抛异常。

翻页链接会保留关键词、栏目等筛选条件，只删除旧 `page` 参数，避免用户翻页时丢失搜索条件。

## 19. 缓存：让读取快一点，但不让旧数据留太久

缓存是数据库前的临时副本，不是最终真相来源。

公开页面使用：

```text
首页：缓存 30 秒
文章详情：缓存 60 秒
```

缓存键有版本前缀，例如：

```text
cms:page:v1:home
cms:page:v1:item:12
```

版本号可以在缓存数据结构变化时整体换一批键，避免旧格式继续被读取。

### 19.1 Redis 与本地缓存

```text
local 模式：LocMemCache，当前 Python 进程内存
public 模式：Redis，独立缓存服务
```

本地缓存不需要额外服务，但多个进程不能共享内容。公网模式要求 Redis，因为缓存和限流需要在运行实例之间共享。

### 19.2 缓存失效为什么放在事务提交后

文章或栏目变更会发出 Django Signal：

```text
模型保存或删除
  -> post_save / post_delete
  -> transaction.on_commit(...)
  -> 删除相关文章详情缓存和首页缓存
```

`transaction.on_commit` 的意义是：只有数据库事务真正成功提交后才清缓存。

若事务最后回滚，数据库没有改变，缓存也不应该被提前删除。这让数据库与缓存的可见状态更一致。

### 19.3 缓存服务故障怎么办

公开页面读取缓存失败时会直接执行 `loader()` 回源查询数据库。缓存是加速层，暂时不可用不应让普通文章阅读完全失败。

## 20. Django Admin：内置的内容管理后台

项目没有另写一套文章编辑 API，而是配置 Django Admin。

文章后台支持：

- 新建、编辑文章和栏目。
- 按状态、栏目、时间筛选。
- 按标题搜索。
- 批量发布。
- 批量撤回为草稿。

`ItemAdminForm` 会对标题和正文执行 `.strip()`，拒绝只含空格、换行或制表符的内容。

批量发布的逻辑是：

```text
管理员选择多篇文章
  -> 一条批量 UPDATE 修改发布状态
  -> 为每篇文章写 Admin 审计记录
  -> 事务提交后批量删除相关缓存
```

这里 `queryset.update()` 适合批量状态更新，避免逐条调用 `save()`。

## 21. 认证、会话和后台权限

项目使用 Django 内置用户模型。

用户界面简化为两类角色：

```text
普通用户：不具备后台访问权
管理员：is_staff=True 且 is_superuser=True
```

但后台总入口还被自定义 `SuperuserAdminSite` 收紧：必须同时满足：

```text
is_active=True
is_superuser=True
```

仅有 `is_staff=True` 的账号不能进入后台。

Django 登录会用 Session Cookie 保存会话。项目设置：

```text
SESSION_COOKIE_HTTPONLY = True
SESSION_COOKIE_SAMESITE = "Lax"
CSRF_COOKIE_HTTPONLY = True
```

- `HttpOnly`：JavaScript 不能直接读取 Cookie，降低 XSS 窃取会话风险。
- `SameSite=Lax`：限制浏览器在跨站请求中自动带上 Cookie 的情况。
- CSRF：Django 用令牌验证带 Cookie 的写操作来自可信页面。

## 22. 中间件：所有请求都要通过的关卡

中间件是请求和视图之间的一层流水线。

```text
请求从上到下通过中间件
  -> 最终视图
响应通常从下到上返回
```

### 22.1 请求 ID 和访问日志

`RequestContextMiddleware` 为每个请求生成 UUID：

```text
X-Request-ID: 9f...
```

它同时：

- 保存线程本地 request ID。
- 统计请求耗时。
- 给响应增加 `X-Request-ID`。
- 写入方法、路径、状态码、耗时、用户编号和脱敏 IP。
- 在 `finally` 中清理线程本地数据。

这样用户报告问题时，运维人员可以用响应头中的请求 ID 找到服务器对应日志。

### 22.2 公开 GET 限流

`PublicRateLimitMiddleware` 针对公开 GET 请求做固定窗口限流。

它以：

```text
客户端 IP + 请求路径
```

作为计数键。超过配置上限时返回：

```text
HTTP 429 Too Many Requests
Retry-After: <秒数>
```

`/admin/` 和 `/health/` 不走这个公开阅读限制。

如果 Redis 不可用，公开读取选择 **fail-open**：记录日志后继续处理页面请求。原因是缓存/限流服务故障不应让普通阅读全部不可用。

### 22.3 登录失败限流

`AdminLoginThrottleMiddleware` 只保护：

```text
/accounts/login/
/admin/login/
```

它按用户名摘要与 IP 记录失败次数。用户名先 `.strip()`、`casefold()`，再算 SHA-256 摘要，缓存键中不直接留原始用户名。

公网模式下限流后端故障会返回 503，即 **fail-closed**。登录是敏感边界，无法可靠统计失败时，宁可暂时拒绝登录，也不降低暴力破解保护。

## 23. 结构化日志与请求关联

日志使用 JSON Lines（JSONL）：

```text
一行日志 = 一个 JSON 对象
```

例如会包含：

```text
timestamp
level
logger
event
request_id
method
path
status
duration_ms
user_id
masked_ip
```

`JsonFormatter` 只允许固定白名单字段进入日志，避免某次调用把密码、Cookie 或其他任意对象意外写入文件。

IP 会脱敏：

```text
IPv4 只保留 /24 网段
IPv6 只保留 /64 网段
```

这样仍能观察粗略来源网络，却不保留完整主机地址。

日志文件按天轮转，保留 14 份。后台系统日志页从文件尾部逆向读取，最多加载 5000 条，并只读取命名规则合法的轮转文件。这避免一个无限增长的日志文件拖垮后台页面，也避免后台任意读取日志目录内其他文件。

## 24. 健康检查：活着与准备好不同

项目暴露：

```text
/health/live/
/health/ready/
```

### 24.1 Live

`live` 直接返回：

```json
{"status": "ok"}
```

它只说明 Web 进程至少还能响应请求。

### 24.2 Ready

`ready` 会：

1. 对数据库执行 `SELECT 1`。
2. 写入缓存探针值。
3. 再读回缓存探针值。
4. 全部成功才返回 200。

数据库或缓存任一失败都会返回 503。

所以：

```text
live  = 进程还活着
ready = 进程、数据库、缓存都能工作
```

部署平台可以根据 readiness 决定是否把流量发送给实例。

## 25. 演示数据：可重复执行的种子命令

`python manage.py seed_data` 同步固定演示数据：

```text
3 个用户
8 个栏目
36 篇文章，其中 3 篇草稿
```

数据规格放在 `content/demo_data.py`，用不可变 `dataclass` 和固定上海时区时间生成，因此相同版本代码总能产生一致演示数据。

命令通过：

```python
with transaction.atomic():
```

把用户、旧管理员迁移、栏目和文章同步放在同一事务中。

事务可以理解成“整批操作要么都提交，要么都撤销”。例如缺少 `DEMO_USER_PASSWORD` 时，命令会在写数据库之前失败，不会留下半套数据。

`update_or_create()` 让命令可以重复运行：

```text
记录不存在：创建
记录存在但内容不一致：更新修复
记录已经一致：跳过
```

注意：文章同步使用“标题 + 栏目”作为自然匹配键，但当前模型未将该组合声明为数据库唯一约束。因此极端并发执行种子命令时，理论上仍可能需要更强的数据库层约束或并发控制。

## 26. 公网安全设置

项目用 `DJANGO_MODE` 区分：

```text
local
public
```

`public` 模式中：

- 必须提供 `DJANGO_SECRET_KEY`。
- 必须配置允许的 Host 和 CSRF 来源。
- 禁止 `ALLOWED_HOSTS = ["*"]`。
- 强制 HTTPS 重定向。
- Session 和 CSRF Cookie 标记为 Secure。
- 启用 HSTS。
- 启用 `X-Frame-Options: DENY`，防止页面被嵌入 iframe。
- 启用 `nosniff`，减少浏览器错误猜测资源类型。
- 限制 Referer 为同源策略。

这些都由 `config/security.py` 根据运行模式构造，再由 `settings.py` 注入 Django 配置。

## 27. 容器部署：Dockerfile 做了什么

Dockerfile 使用多阶段构建：

```text
builder 阶段
  -> 安装 uv 和 Python 依赖到虚拟环境
runtime 阶段
  -> 复制虚拟环境和应用源码
  -> 收集静态资源
  -> 以非 root cms 用户运行 Waitress
```

关键点：

- 不以 root 用户运行 Web 服务。
- 构建时执行 `collectstatic`。
- 暴露 8000 端口。
- Docker `HEALTHCHECK` 请求 `/health/live/`。
- 默认命令是 `python manage.py serve_waitress`。

Docker `EXPOSE` 只是镜像元数据；真实端口能否从宿主机访问，仍取决于运行容器时是否做端口映射。

## 28. 临时公网演示如何工作

`serve_public` 命令不是常规生产发布平台，而是一次性演示启动器。它会：

```text
启动 cpolar 隧道
  -> 从 cpolar 日志找到唯一合法 HTTPS 地址
  -> 把该域名写入子进程环境
  -> 执行 deploy check、迁移、种子数据、静态文件和 preflight
  -> 启动 Waitress
  -> 命令结束时停止自己创建的 Waitress 与 cpolar 子进程
```

这里有两条重要安全边界：

1. 只接受规定 cpolar 域名后缀、无账号密码、无端口、无路径和无查询参数的 HTTPS 根地址。
2. 只终止自己保存的 `Popen` 子进程对象，不按名称扫描并终止机器上其他同名进程。

## 29. 推荐阅读顺序

如果你要从零读懂后端，建议按这个顺序：

1. `manage.py`：了解命令怎样进入 Django。
2. `config/settings.py`：了解应用、数据库、中间件和静态资源总配置。
3. `config/urls.py` 与 `content/urls.py`：了解网址如何指向功能。
4. `content/views.py`：了解请求如何变成页面。
5. `content/forms.py`：了解输入怎样被验证。
6. `content/models.py`：了解数据库表、关系和索引。
7. `content/selectors.py`：了解 ORM 查询如何组织。
8. `core/caching.py` 与 `core/signals.py`：了解缓存怎样失效。
9. `core/middleware.py` 与 `core/throttling.py`：了解请求级安全。
10. `core/views.py`、`json_logging.py`、`log_reader.py`：了解健康检查和日志。
11. `core/management/commands/` 与 `Dockerfile`：了解服务怎样运行和部署。

## 30. 总结

这个项目的后端架构可以浓缩成：

```text
Django 单体 CMS
├── config：全局配置、路由、数据库、安全、服务器入口
├── content：文章、栏目、搜索、分页、Admin 和演示数据
├── core：缓存、事务后失效、限流、日志、健康检查、后台权限、运维命令
├── PostgreSQL：唯一业务数据库
├── Redis：公网缓存与限流后端
├── Waitress：WSGI Web 服务器
└── Django Admin：受限的内容管理界面
```

它遵循的核心规则是：

- 公开查询只读取已发布文章。
- 草稿对外与不存在文章一样返回 404。
- 栏目仍有文章时不可删除；作者删除后文章保留。
- 迁移负责把模型演化为真实数据库结构。
- 索引围绕首页、栏目和标题搜索的真实读取路径设计。
- 缓存只用于加速，数据库才是真相来源。
- 数据库提交成功后才失效缓存。
- 后台只允许活跃超级用户进入。
- 公开读取和登录失败采用不同的限流故障策略。
- 日志使用结构化 JSON、请求 ID 和脱敏 IP。
- 健康检查区分“服务活着”和“服务已经准备好接流量”。

理解这些边界后，你就能从一次普通的“打开文章页面”出发，追踪到 HTTP、Django、ORM、PostgreSQL、缓存、模板和浏览器是怎样协作的。
