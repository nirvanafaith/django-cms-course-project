## 3. 系统架构与内聚耦合分析

### 3.1 三层架构（MTV 细化）

```
┌─────────────────────────── 表现层 ───────────────────────────┐
│  templates/*.html（base/index/item_list/item_detail）         │
│  只消费视图上下文变量，不出现任何 ORM/模型调用                │
├─────────────────────────── 应用层 ───────────────────────────┤
│  urls.py ──► views.py（编排）──► forms.py（校验）             │
│  admin.py（管理端 CRUD 登记）                                  │
├─────────────────────────── 数据访问层 ───────────────────────┤
│  models.py（Category/Item） → ORM 参数化 SQL → SQLite          │
└──────────────────────────────────────────────────────────────┘
依赖方向：表现层 → 应用层 → 数据层，单向、无环。
```

### 3.2 模块内聚性（Cohesion）

| 模块 | 内聚类型 | 说明 |
| --- | --- | --- |
| models.py | 数据内聚 | 仅承载实体定义、约束（unique/db_index/on_delete）、`__str__` 与业务辅助方法 |
| forms.py | 校验内聚 | 所有用户输入校验集中于此，视图不做任何裸解析 |
| views.py | 过程内聚 | 每个视图函数对应用户一个 HTTP 语义动作（index/list/detail/search） |
| admin.py | 注册内聚 | 后台所有登记/列表/过滤配置集中管理 |
| templates | 表现内聚 | 模板只做展示与回显，无业务逻辑 |

### 3.3 模块耦合性（Coupling）

| 耦合对 | 耦合类型 | 控制手段 |
| --- | --- | --- |
| views → forms | 数据耦合 | 视图只调 `form.is_valid()/cleaned_data`，不读内部字段；表单通过 `Meta.model` 绑定模型（DRY） |
| views → models | 数据耦合 | 通过 QuerySet API 访问，禁止原生 SQL；单向引用，models 从不 import views |
| views → templates | 数据耦合（契约式） | 模板变量白名单：`form/items/page_obj/categories/latest_items` 等文档化 |
| forms → models | 数据耦合 | ChoiceField 选项查询集中在 `__init__`；模型不自知表单存在 |
| admin → models | 数据耦合 | Admin 声明式配置，间接依赖 settings/INSTALLED_APPS |

结论：**全部为数据耦合（最低最友好），无控制耦合/内容耦合/外部耦合**；高内聚低耦合可向评审直接陈述。

### 3.4 N+1 查询消除

列表/搜索页中每篇文章需显示所属栏目，若逐行访问 `item.category` 将产生 1 + N 次查询。统一使用：

```python
Item.objects.select_related("category").filter(...)
```

一次 JOIN 解决；并有 `assertNumQueries` 测试锁定（T-IT-16 扩展断言，见 §7）。

## 4. 数据库规范化证明（BCNF 达标论证）

> 题目硬性要求：数据库至少达到 BCNF。以下给出形式化证明。

### 4.1 记号约定

- 属性：`U(Category) = {id, name, description, created_at}`；`U(Item) = {id, title, content, category_id, publish_time, updated_at, is_published, author_id}`
- 函数依赖集 F 由**实体不可分割性 + 主键定义**建立：任何属性均在功能上完全依赖主键。

先说明：`author_id → (auth_user.username...)` 与 `category_id → (Category 属性)` 属于**跨表参照完整性的外键依赖**，归属"表间关联"，不构成目标表内的函数依赖（本表属性不决策任何非键属性），故不可将外键指向的列纳入本表属性集。

### 4.2 Category 表

| 内容 | 结果 |
| --- | --- |
| 函数依赖集（表内） | `Fᶜ = {id → name, id → description, id → created_at}` |
| 候选键 | `K = {id}`（name 有 UNIQUE 约束但仅作辅助候选；任一候选键即含 id 超键） |
| 非平凡依赖判定 | 每条 FD 左端 = `{id}` 即候选键 → 是超键 |
| 结论 | **∀ 非平凡 FD 左端均为超键 ⇒ BCNF ✔** |
| 无传递依赖 | 不存在 `id → A → B`（A 非键）——属性直接依赖主键 |
| 无部分依赖 | 无复合主键，无从谈起 |

### 4.3 Item 表

| 内容 | 结果 |
| --- | --- |
| 函数依赖集（表内） | `Fˡ = {id → title, id → content, id → category_id, id → publish_time, id → updated_at, id → is_published, id → author_id}` |
| 候选键 | `K = {id}` |
| 非平凡依赖判定 | 所有非平凡 FD 左端 = `{id}`（超键） |
| 结论 | **BCNF ✔** |
| 冗余说明 | `publish_time` 加 `db_index` 仅为查询性能，不引入对非键列的传递决策 |

### 4.4 其余表（Django 托管）

`auth_user`、`auth_permission`、`django_admin_log` 等由 Django ORM 自动创建，属于框架自身的规范化结构（官方保证 3NF+）。**作业实体范畴（Category、Item 两表）均已形式化证明为 BCNF**。

### 4.5 删除策略的规范化视角

设计沿用"栏目被引用时禁删（外键 PROTECT）"，该策略不改变函数依赖集，与 BCNF 独立——**删除保护是数据完整性业务规则，非规范化问题**。

## 5. 算法与时间复杂度分析（最优性论证）

数据规模说明：原型定位演示/内网规模（文章 ≤ 10⁵），n_c = 栏目数，n_i = 文章数，k = 单页条数，n_a = N+1 消除后的常数量。

### 5.1 各查询路径复杂度

| # | 查询路径 | 实现 | 最优性论证 | 复杂度 |
| --- | --- | --- | --- | --- |
| 1 | 首页栏目+计数 | `Category.annotate(count=Count("item"))` | 单条 SQL（LEFT JOIN + GROUP BY），避免 每栏目再 Count 的 N+1（后者 O(n_c·n_i)） | O(n_c log n_i)（COUNT 走主键/索引） |
| 2 | /list/ 栏目文章 | `filter(category_id=...)` | 分类外键自动索引 → B 树定位 + 顺序取 k 条；优于全表扫 | O(log n_i + k) |
| 3 | /search/ 时间范围 | `publish_time__range` | `publish_time` 显式 `db_index` → 同样 B 树 | O(log n_i + k) |
| 4 | /search/ 标题 | `title__icontains` | **O(n_i) 已是理论下界**：`LIKE '%q%'` 无前缀可用，任何 B 树/哈希都无法亚线性命中任意子串；若未来数据量爆炸，迁移 SQLite FTS5（设计已记录，不增大模型） | O(n_i)（标注注释） |
| 5 | 组合查询 | 逐条件 append filter | 各谓词独立（可交换）；利用 2/3 的索引，整体 = 最小选择基数分支主导 | O(log n_i + k) |
| 6 | 分页 | `Paginator.get_page()` | LIMIT/OFFSET 常数级取页；首页/末页不重复扫描全表（唯一代价 = OFFSET 跳跃 O(delta)，可接受） | O(log n_i + k) |
| 7 | 列表页 N+1 | `select_related` | 把 1+N 次往返压缩为 1 | 语句 1 条 |

### 5.2 最优性结论（可直接答辩）

1. 除模式 4（模糊子串匹配）外，**全部走索引，达到亚线性下界**；
2. 模式 4 的 O(n) 系该语义的手段——若优化目标含请求，应有 FTS 演进说明；本原型规模 10⁵ 行以内线性扫描 < 10ms，符合工程最优；
3. 分页守卫（page 非法）由 `get_page` 内部降级，无额外复杂度。
